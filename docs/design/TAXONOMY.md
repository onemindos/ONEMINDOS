# App and deployment taxonomy

**Serves:** founder direction of 2026-11-12 ("categorize apps and deployment"; the UI must look good and beat umbrelOS on polish and deployment experience); backlog APP-P1–P3, APP-B3, FAB-P3, DEP-P1 and PLG-P1 in `docs/strategy/core-alignment.md`; contract [`sdk/contracts/poc-v0.md`](../../sdk/contracts/poc-v0.md) §3, §4, §9.3, §11.4; research [`13`](../../research-output/13-apps-market-plugins.md) §3.1, §3.3, §4, §6.
**Data:** [`apps/_intake/candidates.csv`](../../apps/_intake/candidates.csv) columns `category`, `subtags`, `deploy_class`, `placement`, generated by [`scripts/app-taxonomy.py`](../../scripts/app-taxonomy.py). **Read with:** [IA.md](IA.md) §2.2–2.3, [PLUGIN-UI.md](PLUGIN-UI.md), [COMPONENTS.md](COMPONENTS.md) (TrustCard).
**Status:** design. The manifest change in §5 is a **proposal** for a contract amendment; `sdk/schema/` is not changed by this document.

**Plain English.** The Market needs two kinds of labels:
- **What an app is for** (its *category* and a few *sub-tags*). This is how a person browses: "show me photo apps".
- **How an app gets onto the box and how much OneMind vouches for it** (its *deployment class*), plus **what the app needs from the hardware** (its *placement and requirement facets*: which machine, which CPU, a GPU, a USB radio, how much disk, whether it is reachable from the internet). This is how the box decides where an app can run, and how the UI explains it before anything is installed.

Both are data. Every label the UI shows comes from the manifest or the catalog API, so the CLI and agents see the same thing (P4, headless first).

### 1.1 Rules
1. **One category, from the app's main job.** A tool that serves two jobs goes where a person would look first (Paperless-ngx is Files & Photos, not Productivity). Sub-tags carry the rest.
2. **Sub-tags are a closed list per category,** checked by the validator (§5). Free tags lead to "self-hosted", "docker", "linux" noise (that is what free tags in the Cosmos market look like). New sub-tags are added by PR to this table and the script.
3. **Bitcoin and crypto are sub-tags of Finance, not a category.** Research 13 §3.1 keeps them out of launch; their candidate rows stay `parked`, so the Market hides them until the founder decides otherwise. This differs from umbrelOS, where Bitcoin is its own category (88 of 399 apps).
4. **"Media download automation" is the `downloads` sub-tag of Media,** not a category: a person thinks "Media", then narrows.
5. **No "Other" category.** Every app is placed; the 28 research-run "Other" rows were placed by hand in the script's override list.
6. **Robotics joins Field** (research 13 §3.1 lists Robotics separately, filled by adapters later). It holds 9 candidates today; it is first-class because it is OneMind's own ground (TAK, mesh, drones), not because of its size.
7. **Order** is the table order: the founder's daily essentials first (home, files, media, notes), the specialist categories last.

## 2. Deployment classes

The deployment class answers "where did this app come from, and how far does OneMind vouch for it?". It is **derived**, never typed by hand: CI and the gateway compute it from facts (the scan record, the licence class, the source of the manifest, the presence of extensions). The UI shows it as one badge plus a sentence.

| Class | What it is | Who publishes it | Gate | Install button | What the UI shows |
|---|---|---|---|---|---|
| **Core** | Part of the OS: the gateway, `onemindd`, NATS, k3s, the dashboard, the backup agent (restic), the updater. Installed with the image | OneMind, in the signed OS image | OS image CI (contract §10.1) | None ("Part of OneMind") | Neutral badge "Part of OneMind". No Remove; "Updates with the system" links to Updates. Health and logs like any app. Core pieces do not appear in Market browsing, only in Installed and Settings |
| **Market · verified** | A Market app that passed every §9.4 check | OneMind Market index (signed) | §9.4 all checks, scan ≤ 7 days | "Request install" | Green "Verified" pill; TrustCard with licence, scan date, vulnerability counts, archs; "Tested on: amd64, arm64" |
| **Market · community** | A Market app that is listed but cannot reach verified (upstream without releases, archived within limits, single-store, smoke test skipped) | OneMind Market index | Licence, pinning, malware and secrets checks must pass; others recorded | "Request install", then one extra confirm step | Grey "Community" pill and the sentence "Not fully checked by OneMind: <the checks it did not pass>". Hidden behind the "Show community apps" filter (off by default) |
| **List-only** | Listed for completeness, never mirrored or installed by OneMind: source-available (L3), unclear licence (L?), or a proprietary OS image | OneMind Market index, link only | Licence read and classed | None. "Get it from upstream" (external link) | Blue "Link only" pill and why ("Licence does not allow OneMind to ship it: Sustainable Use License"). No placement verdict, no install review |
| **Private** | The owner's own images or manifests (DEP-P1 "Deploy your own"): a compose file, a kustomization, an OCI reference | The owner, on this box only | Same scan as the Market (malware, CVE, secrets) runs on the box or the owner's CI; schema and limits checks always | "Request deploy" | Violet-outline "Private" pill; "Only on this OneMind. Scanned <date>." Never sent to the public index or the website |
| **Plugin** | Any of the above that also adds to OneMind itself: UI extensions (tiles, widgets, settings, notification actions), AI tools, an agent principal (contract §11.2; PLUGIN-SDK.md `spec.extensions`) | As its underlying class | Its class gate **plus** the extension validator (PLG-P2) | "Request install" | A second pill "Plugin" next to the tier pill ("Plugin · Verified"), and an "It adds to OneMind" list in the install review: widgets, settings, tools, and **"Can ask for actions; you approve each one"** for an agent or plugin principal |

**Not a class:** `blocked` (contract §9.3 tier) is a state any Market app can fall into (failed rescan, malware hit). The card keeps its class pill and adds a red "Blocked" pill with the reason; Install is disabled (contract §11.4).

**How the class is derived** (gateway catalog, PROPOSED field `deploy_class` on `GET /v1/apps`):
1. In the OS image's component list → `core`.
2. Manifest from the owner (not from a signed Market index) → `private`.
3. Licence class L3 or L?, or `metadata.listOnly: true` (proprietary OS images) → `list-only`.
4. Otherwise `metadata.tier` from CI: `verified` → `market-verified`, `community` → `market-community`.
5. `plugin` is set **in addition** when `spec.extensions`, `spec.plugin` or `spec.agent` is present. The API returns `deploy_class` plus `plugin: true|false`, so a client never has to parse precedence.

**Headless (P4):** `onemind apps list --class verified --category files` (planned CLI verb) = `GET /v1/apps?deploy_class=market-verified&category=files` (PROPOSED query parameters). An agent sees the same classes through MCP `list_apps` (§11.3).

## 3. Placement and requirement facets

Facets say what an app needs. The box uses them to decide **which node** can run it, and the UI uses them to explain the decision before install ("why not?", FAB-P3, APP-B3).

### 3.1 Facets

| Facet | Values | Manifest source | What the UI shows |
|---|---|---|---|
| **Runs on (node role)** | `hub`, `worker`, `leaf`, `any` | `spec.placement.roles` (PROPOSED §5) | "Runs on: any node" or "Runs on: the hub". On the install review, the node it will go to, chosen by the box, with "Change" listing only nodes that fit |
| **CPU architectures** | `amd64`, `arm64` | `spec.archs` (contract §4) | "amd64, arm64". If no online node matches: "None of your nodes can run it (needs amd64)" |
| **GPU** | none, optional, required | `spec.requires.gpu` (contract §4) + `spec.placement.gpu: optional` (PROPOSED) | "Needs a GPU" or "Faster with a GPU". Placement prefers a GPU node when optional |
| **Memory** | MB | `spec.requires.minMemoryMb` (contract §4) | "Needs 2 GB memory; <node> has 5.1 GB free" (Meter) |
| **Devices** | `usb-serial`, `zigbee`, `zwave`, `thread`, `bluetooth`, `sdr`, `lora`, `camera`, `coral`, `gpio` | `spec.placement.devices` (PROPOSED) | "Needs a Zigbee USB radio" and which node has one (from node capability detection, research 05 §8). Install review step "Device access" names the device path class, never a raw host path |
| **Host network** | true / false | `spec.placement.hostNetwork` (PROPOSED) | Install review step "Network": "Uses the node's network directly (needed for device discovery)". Shown as a permission in the TrustCard "It will be able to" list |
| **Persistent storage** | size, backup on/off | `spec.storage.data` (PLUGIN-SDK.md, PROPOSED) | "Keeps 20 GB of data, backed up" and the target node's free disk; Remove says "data volumes are kept" (APP-P2) |
| **Exposure** | `lan` (default), `mesh`, `public` | `spec.placement.exposure` (PROPOSED): the **most** the app may be exposed; the owner picks within it | "Reachable on: your home network". Mesh = the owner's overlay network (remote access). **Public needs its own approval**, never part of install: a separate `app.expose` request with an alertdialog naming the consequence ("Anyone on the internet can reach the login page") |
| **Update channel** | `security`, `stable`; automerge `patch` / `none` | `spec.updates` (contract §9.3) | "Updates: security fixes install automatically in your maintenance window; other updates wait for you" (contract §10.2) |

### 3.2 Node roles (plain language)
- **Hub:** the main OneMind node. Runs the gateway, the bus and the apps that must have one stable address on the home network (DNS and ad-blocking, the VPN server, the reverse proxy, network boot).
- **Worker:** an extra k3s node that runs apps. Heavy apps (local AI models, large databases, VMs and game servers) prefer workers so they cannot starve the hub.
- **Leaf:** a small or remote machine that joins only through a NATS leaf, without k3s (FAB-B1). It runs **adapters**, not Market apps (research 13 §3.4). `leaf` is reserved for device and field adapters (PLUGIN-SDK.md type 4); no current candidate is `leaf`.
- **Any:** any node that runs apps (hub or worker). This is the default.

### 3.3 The placement verdict
For an app that is not installed, the TrustCard (built, COMPONENTS.md) shows one verdict, then the reasons:
- "Fits on **kitchen-pi**" (green) and the facts that matched.
- "Fits, but **kitchen-pi** is stale (last report 3 min ago)" (amber). Placement never uses a stale node's numbers as if live (P2).
- "No node can run this" (red) with each node and its first failing facet: "garage-nuc: no GPU", "kitchen-pi: arm64 image not published". Install is disabled with that reason.

Data: `GET /v1/apps/{id}/plan` (DASHBOARD.md, PROPOSED) returns `{node, fits, reasons[], stale}` per node; the dashboard renders, it does not decide.

## 4. What the Market shows

The Market is where categories and classes meet. Target layout (IA §2.2 extended):

1. **Search** across names, descriptions, categories and sub-tags.
2. **Category chips** with icons, in §1 order, each with a count ("Media 98"). Phone: horizontal scroll row. Selecting a category shows its **sub-tag chips** as a second row.
3. **Filters** (sheet on phones): "Runs on my nodes" (default **on**: hides apps no node can run, with a "N hidden" line that turns it off), deployment class (Verified, Community, Link only; Community off by default), "Needs no GPU", "Arm64".
4. **Rails on the first screen** (no category selected): "Needs you" (pending install requests), "Recommended for this box" (launch set for the edition, research 13 §3.4), "Verified this week" (newest scans), then one rail per category. Rails are sorted by fit first, then score.
5. **App card:** icon, name, one-line description, category, tier pill (+ Plugin pill), and one fit line ("Fits on kitchen-pi" or the first reason it does not). Exactly one primary action: Request install, Get it from upstream, or Open.
6. **App page:** IA §2.3, with the TrustCard verdict first, the facets of §3.1 in plain words, and the install review steps generated from the facets (only steps that apply: Node → Devices → Network → Storage → Exposure → Review request).
7. **Deploy your own** (Private): paste a compose file, a kustomization folder or an OCI reference. The box shows the same review steps, scans it and creates a `app.deploy` request (PROPOSED action type).

Every action is a request that lands in Approvals (P1). An agent's install request shows "Asked by Hermes Agent" and the agent's reason, and only the owner can approve.

**Where this beats umbrelOS** (patterns studied, nothing copied; umbrelOS is PolyForm Noncommercial): umbrelOS installs on one box, so it never answers "which machine?"; OneMind places across nodes and explains the verdict. Its class model is "official store or community store"; OneMind shows **why** an app is community and what was not checked, the licence class and the scan date on every card. Its install is one click; OneMind's is one click to *request*, with an approval and an audit entry, so agents can propose apps safely.

## 5. Manifest change (PROPOSAL only; `sdk/schema/` is owned by another stream)

Additive to contract §4 and §9.3. Existing manifests stay valid after their category slug is migrated (§1.3).


- **Why `tags` is checked by the validator, not the schema:** the allowed list depends on `category`. A schema `if/then` per category would work but is hard to read; the app validator (`sdk/tools/validate-apps`) and the CI gate check it against one table generated from §1.
- **Why `placement` is separate from `requires`:** `spec.requires` is closed in the current schema (contract fixes its shape). New needs go in a new optional block so no existing manifest breaks.
- **Catalog (§11.4) additions, PROPOSED:** `category`, `tags`, `deploy_class`, `plugin`, `placement`, and query parameters `category`, `tag`, `deploy_class`, `fits=true` on `GET /v1/apps`.
- **Cross-checks for CI:** `hostNetwork: true` or a `devices` entry adds a line to the TrustCard permissions; `exposure: public` requires the `app.expose` action and is never auto-approved; `roles: [leaf]` is refused for apps without `spec.extensions` (adapters only).

## 6. The candidate list, normalised

`apps/_intake/candidates.csv` now carries the taxonomy for all 1199 candidates; counts are in the generated block of [`CANDIDATES.md`](../../apps/_intake/CANDIDATES.md).

- `category`, `subtags`: from the research-run category (`category_v0`), split by rules (for example notes versus productivity), then corrected by a reviewed per-id override list where the research categoriser was wrong (ComfyUI was "Productivity", restic and rclone were "Monitoring").
- `deploy_class` is a **target**, not a CI result: `queue` rows with a release in the last 365 days and at least two stores → `market-verified`; other `queue` rows → `market-community` (for example SearXNG, which publishes no releases); `list-only` → `list-only`; `excluded` (L4) and `parked` (Bitcoin and crypto) → `none`; restic → `core` (the OS backup agent, contract §10.1); Hermes Agent and Uptime Kuma → `plugin` (contract §7, PLUGIN-UI.md §5). No candidate is `private` by definition.
- `placement`: `hub` for the 11 network services that need one stable LAN address; `worker` for AI runtimes and model tools (`llm-runtime`, `image`, `speech`, `audio`, `training` sub-tags) and named heavy apps; everything else `any`.
- Change the rules in `scripts/app-taxonomy.py`, run `python3 -I scripts/app-taxonomy.py`, and commit both files. `--check` exits 1 if the files are out of date (suitable for CI).

**Known limits:** sub-tags come from id patterns, so 40-odd low-ranked rows have none; the first scaffolder run for each app (contract §9.2) reads topics and README and should confirm or correct both category and sub-tags.
