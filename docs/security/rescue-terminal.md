# Threat model: the owner-only web terminal (SEC-TERM-01, #273)

**Status:** built and tested, off by default, not yet run on a real image. The shell opens only after a fresh owner passkey assertion that the gateway on the box verifies (the gateway's own WebAuthn code, `core/onemind_core/identity`). With no owner passkey registered, or the gateway down, every start is refused. **Decision:** D-014 (web terminal = yes, narrowly), amended 2026-11-15: build now, keep it disabled until passkeys, never behind the plain owner token. Code: `internal/rescue/terminal.go`, `audit.go`, `pty_linux.go`.

## What it is
A page in the rescue console (`onemindd rescue`, :7443, its own process and unit) that opens a root shell on the box. A shell is the most powerful thing on the machine, so the point of this note is what stops anyone but the owner, at a chosen moment, from getting one.

## The gates, in order
Each gate is a refusal; a request must pass all of them. Tests: `internal/rescue/terminal_test.go`.

| # | Gate | Refusal | Why |
|---|---|---|---|
| 1 | LAN only, owner token | 403 for public and mesh clients; 401 without the owner token | The console's existing check (CORE-UPDATE-8, D-008). |
| 1b | Valid credential that is not the owner's (an agent token, a non-owner person) | **403**, and a `terminal.denied` line on the chain | AI never actuates, and no agent may ever hold a shell. The credential is real, so 403, not 401. |
| 2 | The switch file `/etc/onemind/rescue-terminal.on` exists and nobody but its owner can write it | 404 | Off by default. The owner turns it on with `onemindd rescue terminal enable` (root on the box). Each change is on the chain first. |
| 3 | A fresh passkey assertion, once, at the start (`Reauther`, `passkey.go`) | 401 when the gateway refuses it; 503 when the gateway cannot be asked or the console has no `Reauther`; 409 on the challenge when no owner passkey exists | D-014: not behind the plain owner token. See "The passkey step" below. |
| 4 | The `terminal.start` line is written and synced | 500, no shell | Fail closed: no record, no shell. |
| 5 | CSRF header and same-origin on every write | 403 | A page open in the same browser cannot start or type into a session with the cached password. |

Also: one session at a time (409), input of at most 4 KiB per request, a 10 minute idle timeout and a 1 hour hard cap, the page's script runs only with a per-response nonce (`script-src 'nonce-...'`, no `unsafe-inline`, no `unsafe-eval`).

## The passkey step
1. The page asks the console for a challenge (`POST /terminal/passkey/options`, owner token, switch on, CSRF). The console forwards the owner's own credential to the gateway's loopback port: `POST /v1/auth/rescue/options`. The gateway makes a single-use challenge valid 120 s (purpose `rescue`, so a sign-in or approval challenge cannot be reused here, nor the reverse), user verification required, allowing only the owner's passkeys.
2. The browser signs it (`navigator.credentials.get`) and the page starts the session with the assertion in the body. The console forwards it to `POST /v1/auth/rescue/verify`. The gateway checks the signature, origin and counter, that the passkey belongs to an active owner (and to the same account when the credential is an account session), and writes `auth.step_up.succeeded` (or `.failed`) on its own audit chain. Only then does the console write `terminal.start`, with the credential id, and spawn the shell.
3. The assertion is spent by that one start. Typing, reading and closing on the open session do not ask again; they need the owner token that started the session (a second owner token gets 404), the CSRF header and the unguessable session id. The 10 minute idle timeout and 1 hour cap bound it; the next shell needs a new touch.
4. The console talks only to a loopback gateway address (`-gateway`, `ONEMIND_RESCUE_GATEWAY`, default `http://127.0.0.1:8080`); a non-loopback value is refused so the owner token cannot be sent off the box. It passes the browser's `Host` so the gateway derives the relying party the passkey was registered for. If the identity setting `origins` is set explicitly, it must include the console's origin (`https://<box name>:7443`).
5. The gateway routes are not in the OpenAPI document, the SDK or the MCP tools, and open nothing: they only check and record an assertion.
Trade-off, chosen on purpose: the passkey store is in the gateway, so with the gateway down the terminal cannot open (the rest of the console still works). A shell that opens without the passkey would be the plain-token door D-014 forbids.

## Not reachable by agents, the SDK or AI tools
The terminal exists only in the rescue process. It is not a gateway route, so it is not in `sdk/openapi/onemind-v1.json`, the generated SDKs, the MCP catalogue or the capability gateway's tools. A test greps the OpenAPI document and the gateway code for it. An agent that holds the owner's token is outside this model (the token is the owner's); gate 3 is what protects against that: a token alone, stolen or leaked, still cannot open a shell.

## Audit
`/var/lib/onemind/rescue-audit.jsonl` is a hash chain in the gateway's line format (`core/onemind_core/audit.py`), so `onemind-audit-verify` checks it; a test cross-checks our lines against the Python verifier. Events: `terminal.start` (session id, client address, passkey credential id), `terminal.end` (session, reason: `owner-closed`, `shell-exited`, `idle-timeout`, `max-duration`; seconds, bytes in and out), `terminal.denied`, `terminal.switch`. It is a separate file from the gateway's chain on purpose: the console must work with the gateway down, and two writers would fork the sequence. A chain that does not verify is never appended to, and then no shell opens.

**Keystrokes are not recorded.** The decision, with reasons: the chain cannot be edited, so a password or key typed into a shell would be kept for good and readable by anyone who can read the log; a recording gives a second place to leak secrets from; and a root shell can edit any log a recorder writes to the same box, so a local recording proves little. What is recorded is who (passkey), from where, when, how long and how much. If the founder wants session recording, it needs to go to a place the shell cannot write (the hub), with redaction; that is a separate decision.

## Residual risks and gaps
- **Needs an owner passkey on the box.** Registered through the gateway's sign-in page (`/signin`, "Add passkey"). Kanidm (#236) is not required: this uses the gateway's own WebAuthn. The "owner opens a shell on a real image" box in #273 stays open until it has been run on one.
- **The unit now allows a pty, but the shell is still a confined root.** `onemind-rescue.service` swaps `PrivateDevices=yes` for `DevicePolicy=closed` with a short `DeviceAllow` list (`/dev/ptmx`, `char-pts`, tty, null, zero, urandom, random) and adds `ReadWritePaths=/var/lib/onemind` for the audit chain. The console itself holds exactly one capability, `CAP_DAC_READ_SEARCH` (CORE-UPDATE-9: root must read the `onemind`-owned 0600 CA key and tokens file). The shell holds none: it is not started directly, because a root process that execs a program hands it the unit's bounding set, so the shell would read every file on the box. It starts through `onemindd rescue-shell`, which empties its permitted, effective, inheritable and ambient sets with `no_new_privs` on, checks they are empty, then execs the shell; with `no_new_privs` the kernel never gives the shell more than that helper held. (util-linux `setpriv` cannot do this here: it has no way to clear the permitted set, and dropping the bounding set needs `CAP_SETPCAP`.) For that the unit takes `capset` back from `~@privileged`, alone; `capset` never raises a permitted set. `NoNewPrivileges`, the read-only file system, the rest of the `~@privileged` syscall filter and `MemoryDenyWriteExecute` all stay, and the shell inherits them. So it can inspect (logs, state, `rauc` and `systemctl` over D-Bus as the unit already does) but cannot, for example, `chown`, mount, or write outside `/var/lib/onemind` and `/tmp`. Whether a rescue shell should be fuller (some capabilities, a writable `/etc`) is a decision for the Opus gate and Zeus; `internal/rescue/unit_test.go` pins today's profile so a loosening shows up in review. The unit is checked as text only (no `systemd-analyze` run), and the PTY code was run in a Debian container; the PTY tests, including the one that reads the shell's capability sets, also passed inside this unit's sandbox under systemd 257 in a Debian 13 container (2026-11-18), and failed closed with `capset` removed from the filter.
- **It is a root shell.** Anyone who passes all gates can do anything on the box, including edit `/var/lib/onemind/rescue-audit.jsonl`. The chain detects edits; it cannot prevent them. Shipping the lines to the hub is the stronger answer (later).
- **Line-mode page.** The browser side is a plain text box with Send and Ctrl-C, no full-screen programs (`vim`, `top`). A real terminal emulator needs a vendored library and its own review.
- **The switch is a file on the box, not a dashboard setting.** The issue says "the owner turns it on in settings"; the dashboard cannot write to a host file, so that needs a gateway to console channel. The CLI is the first slice.
- **Not run on a real image.** Unit tests, a PTY test in a Debian arm64 container, no QEMU battery run.
