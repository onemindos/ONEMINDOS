How the OneMind image works, and how open it should be

What the image is, what is on the disk, how the box starts and updates, what ships inside, how you change it, and the answer to "fully open, or keep what we have?"

Your question: a fully open image, or keep what we have?

Keep what we have and finish it: merge PR 579, so the default image carries CPU microcode and Wi-Fi, network and graphics firmware, and FIRMWARE=no builds a fully open image. Debian, Proxmox VE 9 and Home Assistant OS do the same, because without microcode boxes miss CPU security fixes. Keep the read-only host too; add freedom through apps and plugins. Revisit if a customer needs a certified free system, or if microcode cannot fit inside the signed kernel of PR 594.

01

What an operating system image is

An operating system (OS) is the base software that starts the computer and runs everything else. An image is one finished file that holds a whole OS, ready to write onto a disk. OneMind builds its image from the public repo: a recipe lists every Debian package and every OneMind file, and a build turns the recipe into a disk file plus a signed update file. Every OneMind box of one board type runs the exact same bits, so a test on one box tells you about all of them.

Think of it as: Like a phone's factory software: every phone of one model gets the same signed file. Where it stops: a phone vendor keeps the recipe secret, while ours is public and anyone can rebuild it.

The exact facts, with the file each comes from
  • Recipe: os/rootfs/Containerfile plus the package lists in os/rootfs/packages/ (on main)
  • Build commands: make rootfs, then make image BOARD=x86_64-efi, which writes a disk image, RAUC update bundles and SHA256SUMS to out/image-x86_64-efi/ (Makefile line 6, on main)
  • Base: Debian 13 trixie frozen at the snapshot.debian.org date 20261111T000000Z (os/versions.lock.yaml line 14, on main)
  • A board is one hardware target, such as x86_64-efi, rpi5 or vm, each with its own board.yaml and layout.yaml (os/boards/, on main)
  • A layer is a folder of files copied over the OS tree: base, then onemind, then the board folder (os/rootfs/layers/, on main)

02

What is on the disk

A disk is split into partitions, which are separate areas with their own label, size and filesystem (the way files are organised inside). Our main PC board has seven. Two hold the OS, called slot A and slot B, so one can be replaced while the other keeps running. One big partition, /data, holds everything that changes: apps, settings, logs and the owner's files. The rest are small: a boot area and areas reserved for later.

Think of it as: A house with two identical kitchens and one storeroom. You cook in one kitchen while builders refit the other; your food stays in the storeroom. Where it stops: only one kitchen is ever in use, and the switch happens at a reboot.

  • OS slots onemind-system-a and -b are 10 GiB ext4 each and mounted read-only

  • /data is plain ext4 on main, not encrypted; LUKS2 encryption is in draft PR 577

03

How the box starts

Booting is the chain of steps from power-on to a running system. The motherboard's built-in firmware (UEFI) starts a small program called a bootloader; ours is GRUB. GRUB reads a tiny notes file that says which slot is good and how many times each slot has been tried, picks a slot, and starts that slot's Linux kernel. The kernel then starts systemd, which starts the OneMind services.

  1. You press power and the motherboard's UEFI firmware starts.
  2. UEFI runs GRUB from the EFI system partition (file EFI/BOOT/BOOTX64.EFI), with no signature check on main.
  3. GRUB reads grubenv to see which slots are OK and how many times each has been tried.
  4. GRUB picks the first slot in the order A, B that is OK and has been tried fewer than 3 times, and adds one to its try counter.
  5. GRUB loads that slot's kernel and initrd and starts Linux with the root marked read-only and the slot name A or B.
  6. Linux starts systemd, which mounts /data and bind-mounts the writable folders over the read-only OS.
  7. If /data cannot be mounted, the box goes into recovery mode with a status page on port 8080 instead of starting apps.
  8. Otherwise firstboot (on a new box), k3s, NATS, the gateway and the dashboard start.
  9. After an update, the health gate runs on this boot and either marks the slot good (try counter back to 0) or marks it bad and reboots to the other slot.
The exact facts, with the file each comes from
  • GRUB is built with grub-mkstandalone and is not signed (os/assemble/assemble.py, on main)
  • Slot rule: try a slot while its OK flag is 1 and its TRY counter is below 3; the first usable slot in the order A, B wins (os/assemble/grub.cfg.in lines 1 to 60, copied from Home Assistant OS)
  • TRY goes up by one on each boot; a successful health check resets it to 0
  • If no slot is usable, a menu entry named 'No good slot left: A (ungated fallback)' boots slot A anyway
  • The kernel gets ro (read-only), root=PARTUUID of the slot and rauc.slot=A or B on its command line (grub.cfg.in, on main)
  • No Secure Boot on main; draft PR 594 adds it and draft PR 575 adds a GRUB menu password

04

Why the system part is read-only

Read-only means nothing running on the box can change the OS files, not even by accident. The things that must change are kept on /data and pinned into place with bind mounts (a way to make a folder from one disk appear at a path on another). So the OS is always exactly what we built and tested, and an update simply swaps the whole slot. On main this protection is a mount flag: there is no cryptographic check of the installed OS at boot yet.

Think of it as: Like a printed library book versus your notebook: the book never changes, your notes go in the notebook. Where it stops: on main nobody checks the book's pages for tampering at boot; that would need dm-verity.

The exact facts, with the file each comes from
  • Root is mounted with ro and no rw on the kernel command line (os/assemble/grub.cfg.in, on main)
  • Bind mounts from /data cover /var/log, /var/lib/rancher, kubelet, cni, /var/lib/systemd, /var/tmp, /home, /root, tailscale, /var/lib/onemind-headscale, /var/lib/onemind-nats-leaf, /etc/rancher/node and the file /etc/hosts (os/rootfs/layers/base/etc/fstab, on main)
  • Most of /etc is part of the read-only slot; only the listed paths are writable
  • No dm-verity (integrity check) of the installed root; verity protects only update bundles in transit (os/rauc/system.conf.in line 10, on main)
  • If /data fails, the box enters recovery mode with a status page on port 8080 and never formats, repairs beyond the normal safe boot check, or wipes (os/recovery/README.md, on main)

05

How updates and rollback work

An update is a new signed image of the OS slot, packed as a RAUC bundle (RAUC is the open-source updater we use). The box writes it into the slot that is not running, reboots into it on trial, and runs a health gate: a set of checks that the core services really work. If they pass, the new slot is marked good. If not, the box marks it bad and goes back to the old slot, so a bad update cannot leave the box broken.

Think of it as: Like trying on a new pair of shoes while keeping the old pair by the door: if the new ones pinch, you put the old ones back on. Where it stops: the box decides by itself, using fixed checks.

  1. Every night CI rebuilds the image from a newer Debian snapshot, scans it (SBOM, CVE scan, ClamAV) and runs the QEMU boot tests; the scan steps were not re-read in the workflow.
  2. CI packs the OS slot into a verity-format RAUC bundle signed with the release key and publishes TUF-signed metadata; this stays a dry run until the TUF root and signing secrets are set.
  3. Each hour onemindd on the box checks the channel (security by default) and verifies the TUF metadata against the root shipped in the image.
  4. It downloads the bundle to /data/rauc and checks its length and sha256.
  5. With policy auto it continues; with policy notify it waits for the owner to run onemind update apply.
  6. RAUC checks the bundle's signature, writes a trial marker, then writes the new OS into the slot that is not running.
  7. Inside the 02:00 to 05:00 window, and unless a reboot-inhibit file exists, the box reboots into the new slot on trial.
  8. The health gate needs 3 passing checks in a row, 10 seconds apart, within 300 seconds, plus a version match.
  9. Pass: the slot is marked good and becomes the normal slot. Fail, panic or hang: it is marked bad and the box boots the old slot.
  10. onemindd reports trial, committed or rolled back, and the dashboard Updates page shows the result to the owner.
The exact facts, with the file each comes from
  • onemindd checks hourly; defaults are channel security, policy auto, window 02:00 to 05:00 (internal/update/config.go and /etc/onemind/update.conf, on main)
  • Update metadata is checked with TUF (a signing scheme) against a root shipped in the image; the bundle goes to /data/rauc and its length and sha256 are checked (internal/update/tuf.go, download.go, on main)
  • RAUC accepts only verity-format bundles signed by a key in the image's keyring (os/rauc/system.conf.in, on main)
  • Health gate: 3 passes in a row, 10 s apart, within 300 s, plus a version match; Market apps are not part of it (os/gate/onemind-health-gate.default, on main)
  • Kernel panics and hangs fall back after 3 GRUB tries
  • Publishing is off until you commit the TUF root and set ONEMIND_SECURITY_PUBLISH plus the RAUC signing secrets; no root.json is committed yet (os/update/README.md, on main)

The image holds a minimal Debian 13 system plus the OneMind stack: the updater, the small Kubernetes that runs apps (k3s), the messaging bus (NATS), the private network tools (Tailscale and Headscale), our Go agent and CLI, the gateway and the dashboard. What 'open' means (two different things)

Sense 1, free of closed code: firmware is small software that runs inside a chip (Wi-Fi card, graphics chip); microcode is firmware the kernel loads into the CPU at every boot to fix CPU bugs. Most of it is closed: we may pass the files on but not see or change their source. Sense 2, free to change: can the owner install anything on the host? These are separate. An image can have no closed firmware and still be read-only, or have closed firmware and be editable.

Think of it as: Sense 1 is like a car whose engine computer is sealed by the maker; sense 2 is whether you may open the bonnet at all. Where it stops: closed firmware is not a back door by itself, it is code nobody outside the vendor can read.

The three ways to ship it

A: Firmware included by default, with an open build switch (PR 579, draft, not merged)

Recommended

For

  • Wi-Fi, graphics and CPU security fixes work on real boxes the first time they boot
  • Same choice as Debian's official installer, Proxmox VE 9 and Home Assistant OS
  • One download to support and test
  • A fully open image is one switch away (make image FIRMWARE=no), and the build fails if that switch leaks closed firmware
  • Every closed file is listed in a licence table, packages.txt and the SBOM

Against

  • The default image is not 100 percent free software, so it can never get an FSF endorsement
  • We must ship the vendors' licence notices with the image
  • The size increase has not been measured
  • The open variant needs its own CI job or it will quietly break

B: Fully open by default, firmware as an add-on (the Talos pattern)

For

  • The strongest open claim we could make
  • Smallest base image
  • Matches what main builds today
  • Owners choose exactly which closed parts they accept

Against

  • A box with only Wi-Fi has no network until the add-on arrives, which is a chicken-and-egg problem
  • Boxes run without CPU microcode fixes until someone installs the add-on
  • Needs a signed add-on delivery system we have not built (sysext is planned, not implemented)
  • Two streams to test, and many owners will run the less secure one

C: Two official downloads (with and without firmware)

For

  • A clear choice for each audience
  • The open download can be audited or certified on its own
  • No add-on system needed

Against

  • Double the build, test and support work
  • Owners will pick the wrong one and blame us
  • Debian ran two installer sets for years and voted in 2022 to replace them with one installer that includes firmware
  • Every update has to be built and signed twice
The exact facts, with the file each comes from
  • Sense 1 on main: the x86 Debian image has no closed Debian firmware or microcode by its build files (Components main only); not checked against a built package list (unverified)
  • Sense 1 in draft PR 579: firmware on by default, FIRMWARE=no builds fully open and fails if intel-microcode, amd64-microcode, firmware-* or non-free-firmware appear
  • Not fully open on every board even today: Jetson uses NVIDIA's closed BSP (we publish no Jetson image), and the Pi 5 image targets a closed bootloader EEPROM release but does not ship it
  • Sense 2 on main: the host is read-only and root is locked (passwd -l root in os/rootfs/Containerfile); freedom comes from apps and plugins
  • Open already in other ways: Apache-2.0 licence (LICENSE; D-001 says open core), pinned inputs, SBOM, rebuild from a commit; bit-for-bit identical builds are not proven (unverified)

08

How you can change the image

To change what is on the host, you change the recipe in the repo, build a new image, test it, and ship it as a signed update. You never change a running box by hand. The tests boot the real image in a virtual machine (QEMU) and try good updates, bad updates, panics and power cuts. A change reaches boxes only through the signed update channel.

Think of it as: Like changing a recipe in a bakery's book rather than scraping icing off a cake already sold.

How you add things without changing the image

Most new capability does not need a new image. Apps run as containers in k3s and keep their data on /data, so they install and uninstall without touching the OS. Plugins are apps that plug into named sockets (E1 to E10) of the platform. Some owner settings live on /data and change at once. Host-level add-ons, such as signed system extensions (sysext), are planned but not implemented.

Think of it as: Like a phone: the OS is fixed, apps come and go from the store. Where it stops: our apps can be given more access, but only with owner approval.

A normal Linux compared with ours

On a normal Linux computer the owner types apt install, edits files in /etc and enables services by hand. That is flexible, but every machine slowly drifts into its own unique state, and a bad change can break it with no way back. OneMind trades that freedom on the host for safety: the host is the same on every box, and changes arrive as tested, signed, reversible updates. Freedom moves up one floor, into apps and plugins.

Think of it as: A rented flat with a building manager versus your own house: you cannot knock down walls, but the manager fixes the plumbing overnight and can undo a bad repair.

How competitors do it

Products in our space split into two camps. Appliance systems (Home Assistant OS, Talos, Flatcar, Fedora CoreOS, Ubuntu Core) ship a locked image and update it as a whole, like we do. Software-on-top systems (CasaOS, YunoHost) install on a normal Linux the owner manages. On firmware, Home Assistant OS and Proxmox VE 9 ship closed firmware by default; Talos keeps its base small and offers microcode and firmware as optional signed extensions.

What is not true yet

Several protections are designed and some are in pull requests, but they are not on main today. A pull request (PR) is a proposed change waiting for review; draft means not ready to merge. Until these land, the image is safe against bad updates but not yet against someone with physical access to the disk or the boot menu.

  • No Secure Boot; GRUB is unsigned and its menu can be edited at the keyboard (draft PR 594 signed UKI, which today always boots slot A; draft PR 575 GRUB password).
  • No integrity check of the installed OS at boot; read-only is only a mount flag (no dm-verity of root; no PR found).
  • /data is plain ext4, not encrypted (draft PR 577: LUKS2 with TPM2 unlock and a recovery key).
  • No default-deny host firewall (draft PR 582); nftables is installed but has no ruleset.
  • No closed firmware or CPU microcode in the default x86 image, so some Wi-Fi cards and CPU fixes are missing (draft PR 579).
  • No GPU image variant (draft PR 591) and no update bundles for the installer board (draft PR 581); extra hardening is draft PR 590.
  • Update publishing is off: no TUF root.json committed and the publish switch not set (os/update/README.md).
  • Factory reset wipe not shipped (internal/host/host.go line 180).
  • Recovery partition reserved but empty; boot-a and boot-b partitions empty.
  • Plugins are open PRs 447 to 453; your own app (CORE-DEPLOY-1) and signed sysext (issue 186) are not built.
  • Microcode plus Secure Boot together (PR 579 with PR 594) is untested: microcode must sit inside the signed kernel file.

A–Z

Glossary

Operating system (OS)
The base software that starts the computer and runs all other programs.
Image
One finished file holding a complete OS, ready to write to a disk.
Partition
A separate area of a disk with its own label, size and filesystem.
Filesystem (ext4, vfat)
The way files are organised inside a partition; ext4 is the Linux standard, vfat is what UEFI can read.
UEFI
The firmware built into the motherboard that starts first and runs the bootloader.
Bootloader (GRUB)
A small program that picks which OS slot to start and loads its kernel.
Kernel
The core of Linux that talks to the hardware.
initrd
A tiny starter filesystem the kernel uses before the real OS is mounted; microcode can ride in it.
systemd
The first program Linux starts; it starts and supervises every service.
Slot (A/B)
One of two copies of the OS; one runs while the other can be replaced.
Read-only
Files that cannot be changed while the system runs.
Bind mount
Making a folder from one place appear at another path, used to put writable /data folders inside the read-only OS.
RAUC
The open-source updater that writes signed bundles into the inactive slot.
Bundle
A signed update file that contains a new OS slot.
dm-verity
A Linux feature that checks every block of a disk area against a signed fingerprint; we use it for bundles, not yet for the installed OS.
TUF
The Update Framework: a signing scheme that stops fake, old or replayed updates.
Health gate
Our checks after an update that decide keep or roll back.
Rollback
Going back to the previous OS slot when the new one fails.
Firmware
Small software that runs inside a chip such as a Wi-Fi card or graphics chip; usually closed.
Microcode
Firmware the kernel loads into the CPU at every boot to fix CPU bugs, including security flaws.
non-free-firmware
Debian's separate archive section for closed firmware, created by a 2022 vote.
Secure Boot
UEFI starts only programs signed with a trusted key, so the boot chain cannot be swapped.
UKI
Unified kernel image: kernel, initrd and command line in one signed file.
k3s
A small Kubernetes that runs apps as containers on the box.
SBOM
Software bill of materials: the list of every package and version inside the image.
