# NATS fabric lab, the whole D-029 series in one hub: pass/fail criteria (pre-registered)

**Status:** PRE-REGISTERED. Written 2026-11-25 before the harness (`internal/leaf/na_test.go`, `make na`) existed and before any run of it. Its sha256 at that moment is in `PREREGISTRATION.sha256`, added in a commit of its own before the harness. Nothing here may change afterwards except typo fixes; any other change is a new, dated section at the end. Results never live here (they go to the run's log and CI).

**Serves:** D-029 (the gateway decides; NATS enforces and carries; machines enforce a signed stop and revoke snapshot while offline; agents go through the callout; local programs sign in), design steps N1, N2, N7, N9; issue #156 (fleet jobs). Lane prefix **NA**. **Does not replace** the per-step tests (`internal/leaf/jobs_test.go`, `local_test.go`, `callout_test.go`, `core/tests/test_nats_callout.py`); this suite proves the steps work **together in one hub configuration**.

> **In plain words.** One hub NATS server runs the accounts file exactly as the gateway writes it with everything on: the job queue, the stop snapshot, the auth callout block, two machines. Two machine NATS servers (leaf nodes) run their config exactly as `onemind fabric join` writes it, with local sign-in. The gateway's answering service for the callout is **not** running, as when the gateway is down. The suite checks that machines still get their jobs and their stop snapshot, that local programs must sign in, and that nobody else gets onto the hub.

## 1. Setup and rules

- Real `nats-server` v2.15.3 processes (the version in `go.mod` and `os/versions.lock.yaml`), embedded by the Go test, on loopback: one hub, two leaves (`aaa111`, `bbb222`) with their own JetStream domains, leaf TLS from a fresh test CA. Machine A's link to the hub runs through a TCP relay the harness can cut, so A keeps running while it cannot reach the hub. No VM: this is a composed lab of the fabric's processes; a two-VM run on images is a later section.
- The hub accounts file is rendered by the gateway's own code (`core/onemind_core/natsconf.py`, with JetStream, two nodes, one hub service key, and the callout block) and committed as `internal/leaf/testdata/hub-accounts-na.golden.conf`; `core/tests/test_fabric_policy.py` checks it byte for byte. The job consumer, the job stream and the policy stream come from the gateway's goldens (`node-job-consumer.golden.json`, `policy-stream.golden.json`). Leaf configs come from `internal/leaf` `Config.Render` with `OnemindUser` and `CLIUser` local users.
- Jobs and snapshots are signed with a fresh test key whose public half machine A pins, exactly as at join; the machine side is the real `internal/jobs` intake with `backup.NewNodeJobVerifier` and `jobs.PolicyStore`.
- Keys are made in the run and die with it. **Result states:** PASS, FAIL; a check that cannot run because of the environment is BLOCKED with the reason, never PASS. A harness bug may be re-run once and is named as such. The suite passes when NA1 to NA5 all PASS in one run.

## 2. Criteria

| ID | Criterion | PASS if | FAIL if |
|---|---|---|---|
| NA1 | Pinned machines link up with the gateway down | With the callout block on and no responder, both leaves report their hub link up within 30 s, and a client signing in with the hub service key connects | Either leaf stays down, or the hub service key is refused |
| NA2 | A job reaches a machine that was cut off, once | With A's link cut, a signed job for A (published twice with the same job id) is stored once; after the link returns, A's intake runs it exactly once and its `succeeded` result reaches the hub on `onemind.node.aaa111.jobresult.<job_id>` within 60 s; publishing the same signed job again is refused as a replay and not run | The job is lost, runs twice, the result never arrives, or the replay runs |
| NA3 | Local programs must sign in, each only for its own subjects | On A's leaf a client with no key and a client with an unknown key are refused; onemindd's key publishing `onemind.node.bbb222.status` or `onemind.node.aaa111.job.<kind>` gets a permissions violation and nothing reaches the hub | A keyless or unknown client connects, or either publish is accepted |
| NA4 | The newest stop snapshot wins over queued jobs after a cut | With A cut: a job for A signed under epoch 1 and an actuating job under epoch 2 are queued, a snapshot with epoch 2 and the motion lockout on is published, and a read-only `host.check` under epoch 2 is queued. After the link returns, the epoch-1 job is reported `failed`/`stale_epoch`, the actuating job `failed`/`stopped`, `host.check` `succeeded`, no actuating handler ran, and A's disk holds the epoch-2 snapshot | Any actuating handler runs, a reason differs, or the snapshot is not kept |
| NA5 | Unknown clients are refused while the gateway is down | During the same run, a client signing in with an unregistered agent key and a client with no key are both refused by the hub within the callout timeout | Either connects |
