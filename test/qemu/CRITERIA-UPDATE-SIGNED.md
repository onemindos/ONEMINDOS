# QEMU, a signed update through the real update path: pass/fail criteria (pre-registered)

**Status:** PRE-REGISTERED. Written 2026-11-25 before `updatesigned.py` or the `SIGNED=1` fixtures existed or were booted. Its sha256 at that moment is in `PREREGISTRATION.sha256`. Nothing here may change afterwards except typo fixes; any other change is a new, dated section at the end. Results never live here (they go to the run's `results.json` and CI logs).

**Serves:** #153 / D-010 (the root ceremony: this is the end-to-end proof that a ceremony-shaped root lets a box take a signed update and nothing else), brief 30 B4.2 and B4.3 (the on-box updater and the channel, `os/update/CHANNEL.md`), D-007 (RAUC A/B with a health-gated commit). It is the QEMU rehearsal of Step 5's "publish the first real signed update to the Dell and watch it install and roll back". **Does not replace** `CRITERIA.md` (RAUC install, the gate and bad-image rollback with `rauc install` by hand) or `CRITERIA-ROLLBACK.md` (the owner's go-back).

## 1. Starting state and rules

- **Keys.** Throwaway keys only, made on the build host for this run and deleted after the channels are built: a TUF root of the ceremony's shape (three root keys, threshold 2, two signing, the third trusted by its public key), one targets, snapshot and timestamp key, and an "attacker" set of online keys that the root does not trust. RAUC bundles are signed by the fixture's throwaway dev CA (the image's keyring) or its throwaway "wrong" CA, as in `CRITERIA.md`.
- **The image trusts the root the way a real image does.** The fixture tree carries the rehearsal `root.json` at `/usr/lib/onemind/tuf/security/root.json` (read-only root, the path `onemindd update` trusts). The test never points the updater at another root: its config file sets only `channel`, `url`, `window` and `policy`.
- **The update path is the real one.** `onemind update check|apply --local --no-reboot --config <file on /data>` runs the box's own engine (`internal/update`): go-tuf refresh from the channel URL, download to `/data/rauc`, length and sha256 against the signed targets, `rauc install` (which checks the bundle signature against the image keyring), the gate's trial marker. The test reboots with `systemctl reboot` and reads the health gate's own `RESULT` line. `--local` is the owner's break-glass path at the console (the gateway approval is tested elsewhere); `--no-reboot` only moves the reboot into the harness so the console stays readable.
- **The channel is published with the real publisher.** `os/update/tuf-repo.py build` (the tool the nightly uses) makes the channel metadata from release files, with `--allow-dry-run` because the bundles are signed by throwaway keys. Only the two attack channels that the publisher refuses to make (a channel signed by untrusted keys, and one listing an older version) are written with the python-tuf metadata API in the same format.
- **Network.** A local HTTP server on the build host serves the channel directory; QEMU's user network forwards a guest address to it, and `socat` in the guest listens on `127.0.0.1:8000` (the updater allows plain HTTP only to loopback). The server logs every request path, so the test can tell whether a bundle was fetched. The tampered case flips one byte of the bundle while serving it; the files on disk are not changed.
- **Versions.** The slot-A disk is V1 (`1`); `good.raucb` is V2 (`2`, dev CA); `us-wrongca.raucb` is V3 (`3`, the same tree signed by the wrong CA); `us-old.raucb` is V1 (`1`, dev CA).
- **Channels** (metadata versions in brackets): **C1** = publisher, lists V2 [1]. **C2** = publisher on top of C1, adds V3 [2]. **CK** = C1's targets with metadata [2] signed by the attacker keys. **CO** = metadata [3] signed by the real online keys, listing only `us-old.raucb` as V1.
- Everything is read from the guest console (exit codes, `onemind update status --json`, `rauc status`, files under `/data`) and the server's request log. A test that cannot run because of an environment limit is **BLOCKED** with the reason, never PASS. Every verdict records the board, KVM or TCG, and the host CPU count. A harness bug may be re-run once and is named as such.
- Timeouts (wall clock): first-boot configuration line 900 s; one `apply` 1800 s; gate result as in `CRITERIA.md`.

## 2. Tests (run in this order on one disk)

| ID | Test | PASS if | FAIL if |
|---|---|---|---|
| US0 | Starting state | First boot reaches the configured line; the gate logs `committed-boot slot=A version=1`; the guest's `/usr/lib/onemind/tuf/security/root.json` has the same sha256 as the channel's root; `onemind update check` against C1 exits 0 and prints `decision: install` with V2 available | Anything else (the later tests are then BLOCKED, not failed) |
| US1 | A tampered bundle is refused | Serving C1 with one byte of the bundle flipped: `apply` exits non-zero; the server log shows the bundle was fetched; `status.json` state is `error` and its `last_result` names the download; no `/data/onemind/pending`; no bundle file left under `/data/rauc`; still booted from slot A at V1 | `apply` exits 0, a trial marker or a bundle file is left, or the box would boot anything else |
| US2 | Metadata signed by keys the root does not trust is refused | Serving CK: `apply` exits non-zero; `last_result` starts with `check failed`; the server log shows **no** `.raucb` request; no pending marker; still slot A at V1 | Exit 0, any bundle fetched, or a marker |
| US3 | The good signed update installs, boots and passes health | Serving C1: `apply` exits 0 and prints `decision: install`; state `pending_reboot` with the pending marker naming V2; after `systemctl reboot` the gate logs `mark-good slot=B version=2`; the guest then reports `ONEMIND_VERSION` 2 booted from slot B; after `onemind update check` (the engine reads the gate's verdict on each run; C1 offers nothing newer), `onemind update status --json` says `committed` | Any refusal, a different slot or version, a gate rollback, or a state other than `committed` |
| US4 | A bundle signed by a wrong RAUC key is refused even when the channel lists it | Serving C2: the engine fetches `us-wrongca.raucb` (server log); `apply` exits non-zero; `last_result` starts with `rauc install` (the engine's wording for RAUC's refusal); no pending marker; `rauc status` still shows slot B booted; `ONEMIND_VERSION` still 2 | Exit 0, a marker, or the other slot changed to be booted next |
| US5 | Rollback is refused, both ways | (a) Serving C1 again after C2 (older metadata, a replay): `apply` exits non-zero with `last_result` starting `check failed`, and no `.raucb` request. (b) Serving CO (newer metadata, real online keys, only V1 listed): `apply` exits 0 with `decision: nothing` and a skip line for the V1 bundle saying `not newer than 2`, no `.raucb` request, no marker. And on the build host, the real publisher refuses to list V1 on top of C2 (exit non-zero, nothing written). Still slot B at V2 throughout | Any install or fetch of a bundle, a marker, or the publisher listing V1 |
| US6 | The refusals left the box as it was | After US1-US5, one more `systemctl reboot`: the gate logs `committed-boot slot=B version=2` (committed, no trial); `onemind update check` against CO exits 0 with `decision: nothing`, and `onemind update status --json` state is none of `pending_reboot`, `trial`, `rolled_back` | A trial boot, a rollback, another slot or version |

## 3. Boards and verdicts for this task

- **x86_64-efi** (OVMF) runs US0-US6 in order. Other boards are reported, never required.
- On a host without KVM the run uses TCG and says so; a timeout missed only because TCG is slower is **BLOCKED (TCG timing)**, and the test must then pass on a KVM host before it counts.
- Required for this task's "done": US0-US6 PASS on x86_64-efi.
