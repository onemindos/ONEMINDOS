# QEMU battery, cloud images: pass/fail criteria (pre-registered)

**Status:** PRE-REGISTERED. Written 2026-11-12 before any `cloud-*` image was built or booted and before the test that judges them (`test/qemu/cloudboot.py`) existed. Its sha256 at that moment is in `PREREGISTRATION.sha256` and in the commit that adds it, which comes before the code it judges. Nothing here may change afterwards except typo fixes; any other change is a new, dated section at the end. Results never live here (they go to the run's `results.json` and CI logs).

**Serves:** the founder's request of 2026-11-12 (every deployment boots straight into OneMind), here the cloud deployments: AWS, Google Cloud, Azure, Hetzner Cloud, Proxmox VE. D-007, BD-DO-1 (the cloud layer), `docs/leap/core/IMAGES.md` §3 (first boot). **Does not replace** `CRITERIA.md` or `CRITERIA-FIRSTBOOT.md`.

## 1. What is tested, and what is not

- The test boots **the artifact that is uploaded to the cloud**, unmodified: no test overlay, no autologin. It is driven only the way a cloud user drives an instance: a cloud-init seed, the serial console, SSH as `admin` with the key from the seed, and HTTP to the gateway.
- The cloud's metadata service is **emulated with a NoCloud seed** (FAT, label `CIDATA`) shaped like that cloud's metadata, as the table in §3 says. The real datasources (EC2 IMDS, GCE metadata server, Azure IMDS + wireserver, Hetzner metadata, the Proxmox ISO drive) are **not** exercised; the cloud's datasource order is checked as configuration only. A real-cloud boot is a founder kit.
- The disk is presented through a copy-on-write overlay that is **8 GiB larger** than the artifact, as a cloud volume larger than the image is.
- QEMU uses user-mode networking with `restrict=on` (no route out); the harness reaches the guest only through forwarded ports on 127.0.0.1.

## 2. Rules

- "No human input" between QEMU start or a `reboot` and the end state, as in `CRITERIA.md` §1.
- The owner token is read only from the guest's **console** (serial log).
- The SSH key pair is generated by the harness for the run and deleted after it; nothing is committed.
- A test that cannot run because of an environment limit is **BLOCKED** with the reason, never PASS. A harness bug may be re-run once and is named as such.
- Every verdict records the cloud, KVM or TCG, and the host CPU count.
- Timeouts (wall clock, from QEMU start or from the reboot): first-boot configuration line 900 s; SSH login 900 s; `cloud-init status` done 900 s; gateway `/healthz` 900 s; node listed 600 s after `/healthz`; gate result 1800 s; bundle install 2400 s.

## 3. Clouds, artifacts and the expected datasource order

| Cloud | Board | Artifact tested | Firmware, disk bus | Seed shaped like | `datasource_list` (exact, in this order) |
|---|---|---|---|---|---|
| AWS | `cloud-aws` | `onemind-cloud-aws-<v>.raw` (and its `.raw.xz`) | OVMF, NVMe | EC2: `instance-id: i-` + 17 hex, SSH key in **meta-data** `public-keys`, no network-config (DHCP fallback) | `Ec2, NoCloud, None` |
| Google Cloud | `cloud-gcp` | `disk.raw` inside `onemind-cloud-gcp-<v>.tar.gz` | OVMF, virtio-scsi | GCE: numeric instance id, key in meta-data, network-config v2 DHCP with **MTU 1460** | `GCE, NoCloud, None` |
| Azure | `cloud-azure` | `onemind-cloud-azure-<v>.vhd` (fixed VHD) | OVMF, virtio-scsi | Azure: VM UUID instance id, key in meta-data, no network-config | `Azure, NoCloud, None` |
| Hetzner Cloud | `cloud-hetzner` | `onemind-cloud-hetzner-<v>.raw` (and its `.raw.xz`) | SeaBIOS, virtio-scsi | Hetzner: numeric instance id, key in meta-data, network-config v1: interface `eth0` by MAC, DHCPv4 + static IPv6 `2001:db8::1/64` | `Hetzner, NoCloud, None` |

## 4. Tests (per cloud)

| ID | Test | PASS if | FAIL if |
|---|---|---|---|
| C0 | Artifact | Every file listed in the image directory's `SHA256SUMS` matches it. Per cloud: **aws/hetzner** the `.raw` is 16 GiB and its `.raw.xz` decompresses to the same sha256; **gcp** the `.tar.gz` holds exactly one member, `disk.raw`, whose size is a whole number of GiB; **azure** `qemu-img info` says `vpc`, the file size is the virtual size + 512 bytes (fixed VHD footer) and the virtual size is a whole number of MiB; **proxmox** `qemu-img check` reports no errors on the `qcow2` | Any mismatch or a wrong format |
| C1 | First boot as hub | From the artifact, with the §3 firmware and disk bus: the console shows `ONEMIND-FIRSTBOOT: configured role=hub source=nocloud` and exactly one `ONEMIND OWNER TOKEN: <64 hex>` line, and the gate logs `RESULT committed-boot slot=A` | Missing line, token absent or printed twice, no gate commit |
| C2 | cloud-init as that cloud | SSH as `admin` with the seed's key works and `sudo -n true` succeeds; `cloud-init status` reports `done`; `cloud-init query v1.instance_id` equals the seed's; the platform is `nocloud`; the merged `datasource_list` equals §3 exactly; `/etc/ssh/` holds no host key and `/data/onemind/ssh/` holds the ed25519 host key; the seed's network config is in effect (gcp: MTU 1460 on the interface with the default route; hetzner: an interface named `eth0` carries `2001:db8::1/64`; others: an IPv4 default route) | Any item missing |
| C3 | OneMind answers | Through the forwarded port: `GET /healthz` returns 200; `GET /v1/nodes` with the console's owner token lists this box's node id (read over SSH from `/data/onemind/etc/node-id`) with role `hub`; without a token it returns 401; `GET /` returns 200 with a body whose sha256 equals the image's `/usr/lib/onemind/dashboard/index.html` | Any item missing |
| C4 | Data grows, reboot keeps state | `onemind-data` ends within the last 1 MiB of the 24 GiB disk and `/data`'s ext4 size is ≥ 98 % of that partition; after `reboot` with no input: the console shows `already configured role=hub`, **no** new owner token, the node id and the sha256 of `/data/onemind/gateway/tokens.yaml` are unchanged, and the F1 owner token still gets 200 on `/v1/nodes` | Any item missing |
| C5 | No role: wizard is local-only | Fresh boot of the same artifact with a seed that has the SSH key but **no** `onemind:` key: the console shows `not configured; waiting for the setup wizard`; over SSH `curl http://127.0.0.1:8080/` returns 200; through the forwarded port from outside the guest, `GET /` gets **no** HTTP response within 15 s | The wizard answers from outside, or does not answer inside |
| C6 | A/B update keeps the cloud | The image's own `-next` bundle (built with it, same throwaway CA) installs to slot B; after the reboot the gate logs `RESULT mark-good slot=B`; on slot B the merged `datasource_list` still equals §3, the console shows `already configured`, no new owner token, the node id is unchanged and the F1 owner token gets 200 on `/v1/nodes` | No commit of B, the datasource order lost, or a re-run of first boot |

## 5. Verdicts for this task

- **Required for "done":** C0–C4 PASS on all five clouds; C5 PASS on `cloud-hetzner` (no default firewall on that cloud); C6 PASS on `cloud-aws`. Every other cell is reported, never required.
- On a host without KVM the run uses TCG and says so. A gate deadline missed only because TCG is slower than the gate's budget is **BLOCKED (TCG timing)**, with the measured times, not PASS.
