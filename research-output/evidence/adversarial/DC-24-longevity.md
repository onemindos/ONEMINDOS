# DC-24 · FIPS 140-3 for the public-safety tier: refuter, longevity and vendor-risk lens

**Target conclusion** (`07-security-compliance.md` P0-5, §8.6): the public-safety tier does not force Ubuntu Pro, RHEL or SLE. FIPS 140-3 modules run on Debian: the Go Cryptographic Module #5247 (linux/amd64 and arm64 tested; Debian not named) [C-W6-028, C-W6-029] and the OpenSSL FIPS Provider 3.1.2 #4985 (Debian 11.5 x86_64 tested, no arm64) [C-W6-030, C-W6-031]. CJIS v6.1 also accepts AES-256 under FIPS 197 [C-W6-033]. RKE2's FIPS 140-2 citation is stale [C-W6-025, C-W6-026, C-W6-024]. The recommendation: x86 first, and "Go components are rebuilt with `GOFIPS140=v1.0.0` when FIPS mode is sold".

**Verdict: WEAKENED.** "Doesn't force a base change" survives. "Rebuild Go components with GOFIPS140" is not executable today for the component that matters most, k3s. And Go/CMVP lifecycles mean a self-built FIPS story needs continual upkeep.

## Strongest counter-argument
A validated module that *can* run on Debian is not a FIPS-capable *product*. The Kubernetes distribution OneMind would actually ship (k3s) does not run in Go's FIPS-only mode. The SUSE route that does have FIPS (RKE2) is built on Go+BoringCrypto, which the Go team says is "meant to be removed". On Debian, OneMind would own the FIPS posture of every Go binary, on an OS not named in either certificate, with module re-validations that take about a year. Ubuntu Pro FIPS or RHEL buys that upkeep from a vendor. For a solo developer, the real choice is not "Debian possible vs impossible". It is "OneMind maintains FIPS builds vs a vendor maintains them".

## New sources (searched for regressions, lifecycle cuts, vendor lag)
1. **k3s crashes in Go native FIPS-only mode.** Issue #13651 (open since 2026-02-15): k3s crashes with `GODEBUG=fips140=only` on all Go 1.24+ builds because `cluster/encrypt.go` uses PBKDF2-HMAC-SHA1. The maintainer says the fix requires migrating data to a new bootstrap key *before* enabling FIPS [C-REF-DC-longevity-010]. This directly undercuts "rebuild with GOFIPS140 when FIPS mode is sold" for k3s. It also means existing clusters face a migration step, not just a rebuild.
2. **Go module lifecycle.** v1.0.0 (#5247) is frozen. v1.26.0 was "Pending Review in the CMVP Modules In Process List" as of 2026-04-28. Go+BoringCrypto is "meant to be removed" and is incompatible with native mode. The Go team gives no guarantee about regulatory fit [C-REF-DC-longevity-011]. A fix inside the module means waiting for a new validation. Secondary reporting puts recent validations at an average of 348 days [C-REF-DC-longevity-013].
3. **Vendor lag at SUSE.** The RKE2 FIPS docs, last updated 2026-11-10, still describe FIPS 140-2 only and link the Historical #4407 [C-REF-DC-longevity-012]. Search results point to a SUSE-hosted third-party attestation of RKE2 on BoringCrypto #4735 (140-3). I could not extract its text, so it is **not** relied on here. If confirmed, ADR-001 D4's RKE2 route is less stale than P0-5 says, but it still sits on the BoringCrypto path Go plans to remove.

## What would flip it
- **Toward a vendor base for the hardened tier (refuted):** a named public-safety buyer or CJIS auditor requires the module validated on the exact OS (the author's own flip condition), **or** k3s #13651 remains unfixed when FIPS is first sold *and* RKE2 is unacceptable on Debian. Then the only maintained FIPS Kubernetes-plus-OS stacks are vendor ones (Ubuntu Pro FIPS, RHEL).
- **Toward upheld as written:** k3s merges a FIPS-safe KDF path (watch #13651), **and** a test shows a `GOFIPS140=v1.0.0` k3s starts under `fips140=only` on Debian 13 amd64. Or a readable RKE2 140-3 attestation that names Debian-compatible operation.
- Lifecycle tripwire: Go removes Go+BoringCrypto before RKE2 moves to the native module. RKE2's FIPS story would then reset.

**Recommendation (not applied):** change SEC-13 from "rebuild with GOFIPS140 when sold" to "pending-lab: k3s under `GODEBUG=fips140=only` (blocked by k3s #13651); fallback RKE2 #4735 if its attestation is confirmed". Keep the CJIS FIPS 197 AES-256 route as the day-1 answer, since it doesn't depend on any module certificate.
