# W19 refuter (cost and business): C-W19-048, kernel drivers as per-kernel signed driver packs

| Field | Value |
|---|---|
| Claim | A third party cannot install kernel drivers at runtime. Driver plugins must be per-kernel, OneMind-signed driver packs built by the OneMind pipeline, with one sysext owning the module indexes per kernel (index masking untested, T-W19-02). |
| Lens | Cost and business |
| Protocol | RESEARCH-MISSION.md §2 rule 7; conclusion and cited claims only. |
| Date | 2026-11-10 (re-check by 2027-05-10) |
| Verdict | **weakened** (the constraint is upheld; the "one combined pack" remedy is the costly and unproven part) |

## 1. Re-check of the cited sources
- C-W19-008 (lab log run-1.log L48-L49): the module loaded only with a per-kernel modules.dep, and it tainted the kernel with "module verification failed". Confirmed.
- C-W19-005 (Flatcar sysext doc, saved L437-L441): OEM sysexts "are bound to the OS version they were released and tested with". Confirmed.
- C-STEEL-KRU-013 (Debian SecureBoot wiki): lockdown blocks unsigned modules, and MOK enrolment is console-only. Confirmed.
- Precision: *without* Secure Boot, a third party **can** load a module at runtime; it only taints the kernel. "Cannot install" is true only under Secure Boot lockdown, or as a policy choice. The claim should say so.

## 2. Strongest counter-argument
**The masking inference is now confirmed externally. But the production fix in the field is not "one combined pack", and the combined pack is the most expensive option for a small team.**

1. **Masking is real.** In Flatcar #1576 (open since 2024-11-01), the official nvidia-driver sysext hides the ZFS modules: the merged modules.dep lists nvidia but not zfs, and `modprobe zfs` fails [C-REF-W19-cost-008]. A Flatcar maintainer notes the sysext "still overrides modules.dep, so multiple sysexts may conflict" [C-REF-W19-cost-009]. This settles T-W19-02 against independent indexes.
2. **Flatcar fixed it the other way.** flatcar/scripts PR #2976 (merged 2025-08-12) removes depmod files from *every* kmod sysext and runs depmod in a temporary overlay through a modprobe hook on each activation. Maintainers *rejected* a build-time modules.dep because module versions can differ [C-REF-W19-cost-010]. With a runtime hook, each driver stays an independent sysext with its own release cadence.
3. **A combined pack couples every vendor's schedule.** One CAN adapter fix forces a rebuild, re-test, re-sign and re-ship of every driver for every kernel. On a release cadence across Pi 5, x86 and Jetson kernels, that is a matrix of drivers × kernels × boards on every kernel bump.
4. **Even well-staffed community distros cut per-kernel driver builds.** Universal Blue retired its standalone NVIDIA images on 2026-11-07, including the NVIDIA akmods pins and build logic: "We don't need to maintain the world" [C-REF-W19-cost-003]. That is a direct lifecycle cut of per-kernel out-of-tree driver maintenance. OneMind's pipeline takes on the same burden, plus signing.

## 4. Verdict
**Weakened.** Keep "drivers are built and signed per OneMind kernel by the pipeline". Replace "one combined, signed driver-pack sysext per kernel" with "independent signed driver sysexts with no depmod files, plus a OneMind modprobe/depmod overlay hook (the Flatcar #2976 model)". Also put a hard cap on the number of supported out-of-tree drivers in release 1, and price the drivers × kernels × boards matrix.

## 5. What would flip it
- **Back to upheld (combined pack):** a lab test (T-W19-02) showing that the runtime depmod hook breaks under the read-only RAUC image or with Secure Boot, or adds an unacceptable boot or activation delay on a Pi 5.
- **To refuted:** a required day-one device class whose vendor forbids redistribution of a signed binary module (for example a proprietary NPU or GPU driver). Then the per-kernel pipeline model cannot cover it at all.
