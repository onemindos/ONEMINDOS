# DC-18 · Adding the chain of trust later without a layout change — refuter (security lens)

**Refuter:** REF3, security lens, 2026-11-11. Inputs read: the DC-18 question, the W6 answer (`07-security-compliance.md` §2, P0-4, `qbank/W6.md` Q206–Q209) and cited claims C-W6-046…-051, -056…-061; the §4.3/SB-5 summary lines in `01-FOUNDATION-DECISION.md` that state the current key policy.

## Conclusion under test
Secure Boot, TPM-sealed disk keys and dm-verity can be added later **without a reflash**, if the x86 layout is fixed now: large ESP, systemd-boot with signed UKIs per slot, verity headroom, and **LUKS2 on data from first boot**, so that "turning on TPM later is just adding a key slot". Pi 5 OTP and Jetson fuses are irreversible but compatible with A/B. Current policy (SB-5): unattended unlock bound to PCR 7 plus a signed PCR 11 policy.

## Strongest counter-argument
The layout claim survives; the claim that the *security* can be added later as a key slot does not, and the Jetson half is weaker than "compatible".

1. **An unattended TPM unlock is bypassable regardless of PCRs unless the initrd verifies the volume it unlocked.** The filesystem-confusion attack (Jan 2025) extracted volume keys from systemd-cryptenroll and clevis setups, including one with Secure Boot (lanzaboote), in about ten minutes of physical access: the attacker substitutes a LUKS volume with the same UUIDs, the initrd falls back to a passphrase prompt, and attacker code then runs in the measured state with TPM access. The author states that exposure "does not depend on which PCRs you choose"; mitigations are a TPM PIN or measuring the volume key into PCR 15 and verifying it before executing anything from the volume [C-REF3-DC-security-009]. The SB-5 policy (PCR 7 + signed PCR 11, no PIN, recovery-key prompt as fallback) is exactly the pattern described; signed PCR 11 was not analysed, but the attack runs *inside* the legitimately signed UKI, so a signed PCR 11 policy does not obviously stop it. Adding "a key slot" later without this check gives the appearance of at-rest protection, not the protection — and these appliances sit unattended in homes, greenhouses and vehicles, the physical-access threat model.
2. **This is fixable by image update, which supports the layout claim but not the "later" claim.** PCR 15 measurement and a pre-switch-root check live in the initrd/UKI, so no repartitioning is needed. But the check must exist **before** the first TPM key slot is enrolled on any box; otherwise every enrolled box shipped before the fix has a key that was exposed in the field.
3. **Jetson's chain of trust has had boot-path flaws that only a BSP update fixes.** CVE-2024-0148 let an *unprivileged physical attacker* run code via the UEFI RCM boot mode (fixed only in 36.4.3/35.6.1); CVE-2025-33182 let a privileged user corrupt the device tree through UEFI (fixed in 35.6.3/36.4.7) [C-REF3-DC-security-010, C-REF3-DC-security-002]. Fused secure boot does not protect against firmware flaws in the signed firmware itself. So "add the chain later" on Jetson depends on the update path delivering signed UEFI/BSP updates — which ties DC-18 to DC-07's unbuilt Jetson wrapper and to NVIDIA's requirement that UEFI-secure-boot OTA payloads be built with `--uefi-keys` [C-REF3-DC-security-001]. In NVIDIA's favour, the same guide says image-based OTA can newly enable UEFI secure boot on a device where it was off, which supports the no-reflash claim for Jetson.
4. **Irreversible steps make "later" a one-shot.** Pi OTP key/device-key writes and Jetson fuse burns (C-W6-058, C-W6-059) cannot be revised; a mistake in the first field enrolment is a hardware recall, not a later fix.

## Verdict: **weakened**
The narrow DC-18 question — does the layout need to change later — holds: nothing found requires repartitioning. The answer's framing that TPM-sealed encryption can be "turned on later" as "just adding a key slot" is wrong on security: without LUKS identity verification (PCR 15 or equivalent) or a PIN, the slot is bypassable with brief physical access. Required changes: ship the PCR 15 measurement and verify-before-switch-root in the initrd **before** any TPM slot is enrolled; remove or gate the passphrase fallback in unattended mode; add the filesystem-confusion case to lab X-2R; and make "Jetson BSP/UEFI security updates delivered by the Jetson backend" a precondition of the Jetson chain of trust.

## What would flip it
- **To upheld:** a systemd-documented or lab-shown result that a signed PCR 11 policy (with systemd's own `tpm2-measure-pcr`/PCR 15 handling in the initrd) defeats the volume-substitution attack, so the current SB-5 design is already safe.
- **To refuted:** the PCR 15 check, or the Jetson secure-boot OTA, needs a partition or ESP change (for example, an extra measured partition or a larger Jetson ESP) that the shipped layout lacks.
