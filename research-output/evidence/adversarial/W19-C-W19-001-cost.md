# W19 refuter (cost and business): DC-16 host extension mechanism (C-W19-001 to 009)

| Field | Value |
|---|---|
| Claim | systemd-sysext and confext merge read-only images over /usr, /opt and /etc. They are designed for immutable images, use /var/lib/extensions, and merge only when ID and SYSEXT_LEVEL (or VERSION_ID) match. Debian 13 ships systemd 257.13. Lab W19-1 showed a clean add and remove, and a refusal at level 2.0 on a 1.0 host. |
| Lens | Cost and business |
| Protocol | RESEARCH-MISSION.md §2 rule 7; conclusion and cited claims only. |
| Date | 2026-11-10 (re-check by 2027-05-10) |
| Verdict | **upheld** (with two operating-cost caveats the author must carry) |

## 1. Re-check of the cited sources
- C-W19-001 to 003 match the man page excerpts (saved evidence/sources/W19/systemd-sysext.txt). C-W19-004 (257.13-1~deb13u1) is cited from the sources.debian.org API.
- Lab W19-1 README and logs: H1, H2, H4 and H5 PASS. The refusal line `Extension 'onemind-future' is for API level '2.0', but running on API level '1.0'` is present. The lab's stated limits are fair: a mutable-root VM, n=1, no verity and no Secure Boot.

## 2. Strongest counter-argument
The mechanism facts are correct. The cost risk is in how the mechanism *fails*:

1. **One bad image blocks every merge.** systemd #32762, opened 2024-05-11 against 256~rc1, is still open, and its fix PR #32967 is also open. systemd-sysext must mount each image to read its extension-release, and "If one image fails to mount, then no extension is merged". Poettering agrees it should "apply what we can, and skip but log" [C-REF-W19-cost-005]. Once OneMind turns on verity-signed extensions (C-W19-049 item 4), a single unsigned, corrupt or wrongly keyed file in /var/lib/extensions could leave a box with **no** host extensions: no drivers, no profile, nothing merged before k3s. At fleet scale that is support cost. The lab ran without verity, so it could not see this. The author should confirm the behaviour on systemd 257.13.
2. **The level match bites both ways.** Every SYSEXT_LEVEL bump invalidates every installed extension at once. Choosing the wrong versioning axis has already cost one project a redesign: Bluefin's k3s sysext was versioned on the OS-release axis, so a k3s security patch could not ship without an OS point release, and every OS point release re-downloaded an unchanged extension [C-REF-W19-cost-006]. A SYSEXT_LEVEL policy, saying what bumps it and how often, is a business rule the conclusion does not yet state.

Neither point refutes the mechanism. Both are operating costs.

## 4. What would flip it
- **To weakened:** the T-W19-01 extension of the lab, with verity-signed images on Debian 13 systemd 257.13, shows that one invalid image stops every other image from merging, and no option (for example a graceful mode from PR #32967) is in the shipped systemd. The mechanism is then fragile until a per-image quarantine is built.
- **To refuted:** extensions fail to re-merge after a RAUC slot switch with an unchanged SYSEXT_LEVEL (T-W19-01), or Debian 13's systemd lacks confext features the profile design needs.
