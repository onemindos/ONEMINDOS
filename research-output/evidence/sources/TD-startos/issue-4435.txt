TITLE: [bug]: Intel AX200 WiFi dead after 0.3.5.1 → 0.4.0.1 migration — iwlwifi firmware missing from image

### Prerequisites

- [X] I have searched for existing issues that already report this problem.

### Server Hardware

Start9 Server (x86_64) with Intel Wi-Fi 6 AX200

### StartOS Version

0.4.0.1 (migrated from 0.3.5.1)

### Client OS

Linux

### Client OS Version

Arch (kernel 7.1.9)

### Browser

N/A (diagnosed over a shell)

### Current Behavior

After migrating from 0.3.5.1 to 0.4.0.1, WiFi stopped working entirely. The
hardware is present and the driver loads — but the firmware files are not in the
image, so no interface ever appears.

- The AX200 enumerates on PCI.
- `iwlwifi` is loaded, with **zero devices bound to it**.
- `/lib/firmware` contains **20 files and no iwlwifi blobs at all**.

That combination is the tell: a loaded driver with no bound devices is a missing
firmware problem, not a missing driver problem. I initially misdiagnosed it twice
— first as undetected hardware, then as a dropped driver — before checking
`/lib/firmware` and finding it essentially empty.

This appears to be the same omission as **#3624** ("Pi 4 image missing brcmfmac
firmware, no wlan0 (0.4.0.1)"), on different silicon. That issue was fixed in
**#4013**, which added `firmware-brcm80211` to the Raspberry Pi images and
verified that *"the firmware remains Pi/nonfree-specific"* — so the fix was
deliberately scoped to Pi, and x86 hardware with Intel wireless was left without
`firmware-iwlwifi`.

Worth noting this is WiFi on hardware Start9 sells, and #3624 observed the Pi
case was itself a regression of a 2023 fix (#2318).

### Expected Behavior

The x86 image should ship `firmware-iwlwifi` so Intel wireless works out of the
box on Start9 Server hardware, and so a 0.3.x → 0.4.x migration does not
silently remove working WiFi.

### Steps to Reproduce

1. Run 0.3.5.1 on Start9 Server hardware with an Intel AX200, with WiFi working.
2. Migrate to 0.4.0.1.
3. `ip link` — no wireless interface.
4. `lsmod | grep iwlwifi` — the module is loaded.
5. `dmesg | grep iwlwifi` — firmware load failures.
6. `ls /lib/firmware` — 20 files, no `iwlwifi-*` blobs.

### Anything else?

Workaround that restored WiFi immediately: copy 7 iwlwifi blobs into
`/lib/firmware`, then `modprobe -r iwlwifi && modprobe iwlwifi`. The interface
came up and associated on the first attempt.

**Caution for anyone copying that workaround**, learned from #3624: a plain copy
into `/lib/firmware` is almost certainly lost on the next OS update, because it
is not in the persistent overlay. #3624 documents the durable location as
`/media/startos/config/overlay` — noting that `/media/startos/root/config` is
the same btrfs subvolume mounted **read-only**, so the writable path is the one
without `root`. Anyone applying a manual firmware fix should stage it there as
well as live, or WiFi will disappear again at the next update with no obvious
cause.

### Impact beyond WiFi

The lost WiFi was not a standalone inconvenience. On this box it took DNS down
with it, and the resulting resolution failure then caused a *service migration*
to fail during the same upgrade — which presented as an unrelated package
problem and cost several hours to trace back to the firmware. A missing-firmware
regression on the network interface has a wide blast radius during an upgrade,
which seems like an argument for catching it in image CI rather than in the
field.
