1.3           Products covered by other CRA harmonised standards
Some product categories that provide functionality overlapping with an operating system are covered by their own CRA
harmonised standard. Where such a standard exists for a product category, that standard applies to it. These categories
include:

   •     Hypervisors and container runtime systems that support virtualised execution of operating systems (Annex III,
         Class II, point 1 of Regulation (EU) 2024/2847 [i.1]).

   •     Boot managers (Annex III, Class I, point 8 of Regulation (EU) 2024/2847 [i.1]).

For products that embed or interact with an operating system while having a different core functionality, manufacturers
may refer to the present document as one part of demonstrating compliance for the operating system component.

4.7.2         Basic use cases

4.7.2.1       UC-REST: Restricted operating system
An operating system that, as placed on the market, serves a restricted and bounded purpose and is not a general-purpose
computing platform: it does not allow the end user to install and run third-party software without restriction, and it does
not, by default, serve as an extensible platform for unrelated applications. Examples include operating systems
integrated into appliances, sensors, and controllers. A restricted operating system begins from the lowest baseline risk-
factor levels in clause 4.7.5; the capabilities and exposures it does have are added through the conditions of clause 4.7.3.

5.2.5.1        MI-KEVD: Documentation for secure update before or during first use
Assessment criteria: [AC-KEVD]

The product shall be accompanied by documentation describing how the product may be securely updated, including
how to update the product prior to, or as part of, first use.

   •      Applicability: The product has firmware or software update capability

5.2.5.2        MI-KEVA: Secure update before or during first use
Assessment criteria: [AC-KEVA]

The product shall implement a secure update mechanism that operates by default, including before or during first use.

The product shall provide a clear and easy-to-use mechanism allowing an authorised user to opt out of automatic
security updates.

If an authorised user opted out of automatic security updates, the product shall provide, before or during first use, a
mechanism to inform the user to initiate or postpone the update.

5.2.5.5        MI-SUDP: Anti-rollback protection
Assessment criteria: [AC-SUDP]

The product shall maintain a monotonic version counter or an equivalent mechanism to prevent the unauthorised
installation of an earlier software version.

   •      Applicability: The product has firmware or software update capability

5.2.5.6        MI-SUAR: Authorised rollback
Assessment criteria: [AC-SUAR]

Where the product supports intentional, user-initiated rollback to an earlier software version, the rollback shall require
explicit authorisation. Automated recovery mechanisms that revert to the immediately preceding operational state
following a failed update or boot failure are considered recovery actions and are exempt from this explicit authorisation
requirement.

   •      Applicability: The product supports intentional, user-initiated rollback to an earlier software version

5.3.2         SP-REST baseline mitigations
A restricted operating system (UC-REST) implements the following mitigations regardless of any condition. They
address the known-vulnerability threat to a product that receives updates, and require state of the art cryptography in
accordance with Annex K wherever the product uses cryptography; every other mitigation is contributed by a condition
in clause 5.3.4:

   1)    (KEVD or KEVA)

   2)    KEVM

   3)    SCUE

   4)    SUVI

   5)    SUDP

   6)    SUAR

   7)    CRYP


5.3.3         SP-GEN baseline mitigations
A general-purpose operating system (UC-GEN) implements the following mitigations regardless of any condition:

   1)    (KEVD or KEVA)

   2)    KEVM

   3)    SCUE
