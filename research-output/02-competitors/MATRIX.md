> ### Explain it like I'm the founder
> We took apart 13 products that each solve part of what OneMind wants to do. This page lines them up in one grid so you can see, row by row, what each one is built on, how it updates itself, whether it can undo a bad update, how it proves an update is genuine, how apps are packaged, whether it runs Kubernetes, what it does with AI, how it backs up, who can log in, what hardware it runs on, whether it touches robots or IoT, how it makes money and how big the team is.
>
> Four things jump out:
> 1. **Nobody checks that an update really worked before keeping it.** Seven products swap in a whole new OS copy (A/B). Every one of them keeps the new copy as soon as one of its own programs starts, or as soon as boot reaches a certain point. None waits until the box is actually doing its job. OneMind's lab-tested rule (keep the update only after fresh signs that k3s and the core services are healthy) is stricter than all of them.
> 2. **Signing is the weak spot of the industry.** Only StartOS signs both OS updates and apps today. umbrelOS signs only in a beta, Olares uses an MD5 checksum, and TrueNAS checks checksums but not signatures.
> 3. **No one does robots.** Across 11 code bases we searched, zero files mention ROS 2 or MAVLink (the drone protocol). Home Assistant is the IoT champion, with Zigbee, Z-Wave, Matter, Thread, MQTT and Modbus, but it stops at robot vacuums and lawn mowers. Robotics is genuinely open ground.
> 4. **Small teams ship these OSes.** umbrelOS's code came from five people in the last year, and three of them wrote 99% of it. Project N.O.M.A.D. has about two maintainers. So a solo founder *can* do this, but the real risk is the same one they all carry: if one key person leaves, the product stalls.
>
> **How to use it:** the "Constraint fit" column says whether a product's situation (hardware, team, Kubernetes, robotics) is close enough to OneMind's that we should copy its choice by default (mission rule 2). The "What OneMind copies" column lists the patterns we take. We copy patterns, not code, unless the licence is Apache-2.0-compatible.

## 1. How to read the matrix

- **One matrix, four slices.** The 17 requested columns do not fit one screen, so the matrix is split into four tables with the **same rows in the same order**. Read across the four slices for one product.
- **Rows:** 13 products (CasaOS and ZimaOS are split because they differ at every layer), then **OneMind's target** from `01-FOUNDATION-DECISION.md` as the yardstick. Tier A teardowns are marked **(A)**, Tier B **(B)**.
- **The three founder-flagged repos** (REA, Craft Anything, BLA) are tools, not operating systems. Most OS columns do not apply to them, so they get their own short table (§3).
- **Pins:** each cell reflects the release or commit pinned in its teardown. Olares was read at `main` (`e7fe1c96`), not at stable 1.12.7. Its update cells may differ on 1.12.7 (critic gap 19, still open).
- **"Absence" cells** (for example "no robotics") rest on code searches of pinned trees [C-MATRIX-002]. A search finds words, not capabilities, so treat them as "nothing built in".

**Constraint-fit scale** (mission rule 2): **Default** = constraints match, so copy the pattern by default for that layer. **Candidate** = partly matches, so it is one option among others. **Low** = constraints differ, study only. **None** = no useful match.

## 4. Patterns that recur

1. **Every A/B product commits too early.** HAOS (Supervisor start) [C-TD-home-assistant-os-018], umbrelOS (daemon start) [C-TD-umbrelos-019], ZimaOS (services started) [C-TD-casaos-zimaos-013], balenaOS (engine + VPN) [C-TD-balenaos-019], Kairos (early boot stage) [C-TD-kairos-022] and Talos (possibly stale NodeReady) [C-TD-talos-017]. Real failures followed: a box with dead networking marked itself good [C-TD-home-assistant-os-044]; a box whose update daemon fell off D-Bus stayed "good" [C-TD-casaos-zimaos-045]; a node stuck unconfigured never rolled back [C-TD-talos-020]. OneMind's fresh-signal gate is stricter than all six [C-LAB-debian-rugix-023].
2. **A/B protects only what is duplicated.** Shared boot partitions and data are where updates still break boxes: ZimaOS overwrites its boot partition in place [C-TD-casaos-zimaos-011], a Kairos upgrade bricked all three images through the shared boot partition [C-TD-kairos-031], StartOS rewrites one shared `/boot` [C-TD-startos-016], Proxmox users landed at a `grub>` prompt [C-TD-proxmox-ve-019], and a Talos rollback could not undo data-partition damage [C-TD-talos-021]. Pre-reboot data migrations defeat rollback [C-TD-casaos-zimaos-014].
3. **Signing arrives late, and apps are rarely checked on the device.** umbrelOS stable is unsigned [C-TD-umbrelos-011], Olares uses same-origin MD5 [C-TD-olares-004], TrueNAS checks checksums only [C-TD-truenas-scale-008], Kairos makes it opt-in [C-TD-kairos-026]. HAOS never verifies app images [C-TD-home-assistant-os-024], nor does balena [C-TD-balenaos-029]. StartOS is the one product that signs both OS and apps [C-TD-startos-014][C-TD-startos-024].
4. **Small teams pick Debian; board-by-board images take bigger teams.** umbrelOS, StartOS, Proxmox and TrueNAS all build on Debian [C-TD-umbrelos-003][C-TD-startos-005][C-TD-proxmox-ve-003][C-TD-truenas-scale-004]. Buildroot (HAOS, ZimaOS) and Yocto (balena, ~15 OS committers) carry every package and board themselves [C-TD-home-assistant-os-003][C-TD-casaos-zimaos-005][C-TD-balenaos-055].
5. **Kubernetes is rare on single boxes.** Only Olares, Kairos and Talos run it [C-TD-olares-021][C-TD-kairos-042][C-TD-talos-027], and TrueNAS left k3s for Compose [C-DEC-007]. Its app migration stranded third-party catalogue apps [C-TD-truenas-scale-018]. That is why OneMind's app format must not depend on k3s-only features (REC-DEC-10).
6. **MCP is spreading faster than permissions.** umbrelOS shares one grant set across agents, which act as the owner [C-TD-umbrelos-037]; StartOS exposes 208 admin tools by default [C-TD-startos-030]; ZimaOS's MCP server logs in with the admin password [C-TD-casaos-zimaos-038]. Only HA (admin-only, read-only) and TrueNAS (confirmations, preview) add guard rails [C-TD-home-assistant-os-040][C-TD-truenas-scale-034]. None has per-agent scopes, approvals and an audit log together.
7. **No one ships robotics.** Zero robotics-protocol files in 11 pinned trees [C-MATRIX-002], none in Olares [C-TD-olares-048]. Jetson appears only as a fleet target (balena, Kairos) [C-TD-balenaos-042][C-TD-kairos-015]. IoT depth lives in Home Assistant [C-MATRIX-001].
8. **The money is in boxes and the stable channel.** Hardware plus a free OS (umbrelOS, Olares, Start9, Zima) [C-TD-umbrelos-047][C-TD-olares-046][C-TD-startos-039][C-TD-casaos-zimaos-032]; or a free OS with paid stability and support (Proxmox, Kairos, Talos, balena) [C-TD-proxmox-ve-036][C-TD-kairos-049][C-TD-talos-037][C-TD-balenaos-052]. Long support periods are either paid or missing [C-TD-balenaos-039][C-TD-kairos-036][C-TD-talos-003].

## Glossary

| Term | Meaning |
|---|---|
| **A/B update** | Two copies of the OS. The update goes into the spare copy; if it fails, the box boots the old one. |
| **Commit / mark good** | Telling the bootloader "keep this new copy". Before that, a failed boot falls back. |
| **Health-gated commit** | Commit only after checks prove the box works. "Fresh" means the checks read new signals from this boot, not leftovers from the last one. |
| **Rollback** | Going back to the last working version, ideally automatically. |
| **Retry-forward** | Trying the failed update again instead of going back (Olares). |
| **Signing / offline root** | A cryptographic stamp that proves an update is genuine. An offline root key lives on a hardware device, never on a networked computer. |
| **Verity (dm-verity)** | A kernel feature that checks every block of a read-only image against a signed hash tree. |
| **Buildroot / Yocto** | Toolkits that build a small custom Linux from source, usually one image per board. |
| **live-build / debootstrap** | Debian's tools for building an image out of Debian packages. |
| **Meta-distribution** | A layer that turns other distros into one standard appliance format (Kairos). |
| **Boot environment** | A full bootable copy of the OS stored as a ZFS dataset; you can keep many (TrueNAS). |
| **ESP / shared boot partition** | The small partition the firmware boots from. If it is not duplicated, it is a single point of failure. |
| **k3s / Kubernetes** | Software that runs and heals containers across one or many machines. k3s is a small edition. |
| **Docker Compose / Helm** | Two ways to describe apps: Compose for one Docker host, Helm for Kubernetes. |
| **System extension (sysext)** | A signed or verity-protected add-on image overlaid onto a read-only OS, used for drivers or profiles. |
| **MCP** | Model Context Protocol, the standard way AI agents call tools on a system. |
| **ROS 2 / MAVLink** | The main robot software framework, and the main drone messaging protocol. |
| **Constraint fit** | Whether a competitor's situation (hardware, team, Kubernetes, robotics) matches OneMind's closely enough to copy its choice by default. |
| **Bus factor** | How many people would have to leave before a project stalls. |
| **Open core** | The base product is free and open source; some features, support or hardware are sold. |
