A hub whose k3s state was damaged by a power cut repairs it, or asks the owner first (VM 501 test, bug 1, part 2 of 2: recovery, stacked on the durability PR). Before every k3s start, damaged k3s state (empty or torn certificates, tokens, node password or config) is moved aside under /data/onemind/k3s-recovery, never deleted, and k3s makes it again. When only the agent's own certificates, keys and config are damaged, only those move and the cluster and its apps are kept. The owner's data, the apps' volumes, the image store and the gateway database are not touched, and every repair is logged, shown on the console and recorded. Only a hub is repaired; if its role file is damaged, the role in first boot's state.json is used, and a configured box with no readable role says so instead of staying silent. If rebuilding the cluster would need the owner (their apps are in the cluster, the datastore cannot be read, or it was repaired three times in an hour), nothing moves and k3s is held, not started, so nothing writes over the old state; a datastore that cannot be read is also copied aside. The rescue console (port 7443) shows the state and offers Reset k3s state, which needs the owner token and a typed confirmation and then starts k3s again. After a reset, apps must be installed again; their old volumes stay on the disk. New pre-registered QEMU criteria F27 (damaged state repaired, owner data intact), F33 (agent certificates repaired alone, the app kept), F28 and F28h (owner's app present: no automatic repair, k3s held with the datastore untouched, then the approved reset) run in make powercut. Refs #234.
