Encrypted data, slice 1 of IMG-05 (#152), built on the founder's disk-encryption decision of 2026-11-22. On a box's first boot a blank data partition now gets btrfs instead of ext4, with three subvolumes: @ (the default one, which is what /data mounts), @storage (files) and @snapshots (for a later snapshot step). A box with a TPM puts that btrfs inside LUKS2 and unlocks it by itself after every restart; its recovery key is shown once for the emergency kit. A box without a TPM (a Raspberry Pi 5, for example) stays unencrypted so it can come back by itself after a power cut, unless the owner boots it the first time with the kernel command line word onemind.data_encrypt=passphrase: it then asks twice on the console for a passphrase, of at least 8 characters, that will be typed at every restart, and still makes a recovery key. The passphrase and keys only ever go to cryptsetup on stdin, never on a command line or into the journal. The random first key's slot is now really wiped (cryptsetup checks the key against the other slots, so the recovery key is given on stdin). /etc/fstab mounts /data as auto, so ext4 boxes installed earlier keep working and are never converted. A box whose firmware announces a TPM 2.0 (the ACPI TPM2 table, or the TPM event log with kernel-reported version 2, as systemd checks) but whose TPM driver did not come up is still encrypted, with the recovery key, never left plain; a TPM 1.2 (older office PCs) does not count, so such a box follows the no-TPM rule. btrfs-progs is added to the Debian package list. The setup-screen wording waits for PR #921 and the QEMU battery cases (power cut, passphrase unlock) wait for PR #837.

Slice 2 (plan PR 5, the Debian bones): the x86_64-efi (and x86_64-efi-nvidia) and cloud-proxmox images now ship the data partition blank by default, so a new box gets btrfs on its first boot, inside LUKS2 when it has a TPM (D-020), with no `DATA_FS=luks2` build flag. The subvolumes are now @ (k3s and the databases, never snapshotted) and @storage (the owner's files, mounted at /data/storage by data-storage.mount only on a btrfs box), with a `.snapshots` subvolume inside @storage for snapper (the top-level @snapshots is gone). /data is mounted with x-systemd.growfs, and onemind-data-extend now grows an encrypted or btrfs /data too: partition, then the LUKS2 volume, then the filesystem (it used to skip an encrypted volume). The data partition has its own partition type GUID instead of the generic Linux one. The cloud grow service runs the same program, so btrfs and LUKS2 grow on a Proxmox VM as ext4 did. New QEMU checks E5 (no TPM: plain btrfs, layout, type GUID), E6 (update and rollback keep the encrypted /data) and E7 (growth to a 64 GiB disk, encrypted), pre-registered in test/qemu/CRITERIA-DATABTRFS.md. The unlock binding stays TPM2 PCR 7 plus the recovery key.
