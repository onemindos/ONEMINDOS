Every owner gets an emergency kit, and the kit carries the disk key (gateway permissions design 25a, D-020). The kit can now be made before any backup destination exists; a destination added later gets the owner key when the owner types the printed key back (Settings, Recovery and reset, or onemind backup kit attach), because the box never keeps a copy. When the data disk is encrypted, the kit takes the disk recovery key from the storage service once (the file the first boot leaves in RAM, which the storage service now also serves) and prints it; it is in the one-time answer only, never in the database, the audit log or an event, and the general recovery-key route stays off. A new kit only adds a key, so snapshots the old kit opens stay openable, and the kit remembers when the disk key was printed in an earlier kit. New: POST /v1/backups/kit/attach, missing_on and disk_key in GET /v1/backups/kit, onemind backup kit and onemind backup kit attach, the disk key on the first-run kit screen. Fixed the lock-out found on a real hub (Refs #1232): once the owner had a passkey, issuing the kit always failed, so the setup wizard came back after the first backup destination and could not finish. Now the first POST /v1/backups/kit names its request, the owner's passkey signs that request, and the same route shows the kit exactly once (the dashboard does this by itself). Approving a kit request in Approvals is refused, because that answer shows nobody the key: before, it said succeeded, kept the key in memory where no route returns it, replaced the owner's kit and could use up the disk key. New: onemind recovery kit issue with --out FILE (a new 0600 file, never overwritten; ported from #1124), which stops with a pointer to the dashboard when the box has a passkey. If the kit is issued but the file cannot be written (a full USB stick, for example), the command removes the partial file, prints the page on the terminal as the only copy and still fails, so the one-time disk key is never lost.
