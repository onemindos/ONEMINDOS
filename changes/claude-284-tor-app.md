NET-TOR-01 (#284, PR B2): the gateway path for the Tor app. On install and update the gateway writes ConfigMap `onemind-gateway-path` with the address of a new plain-HTTP Tor listener (`ONEMIND_NET_TOR_PORT`, 8446 on an installed box) into the app's namespace and opens one egress allowance to exactly that IPv4 address and port. Every request on that listener is the `tor` path (the listener sets it, never the peer address or a header), so a private or mesh app is 404 over the onion even though Tor reaches the gateway from a pod address that reads as the LAN; the listener is plain HTTP because Tor forwards raw TCP and the onion origin is http://, so it binds only to the hub's mesh address (never the wildcard or LAN, contract section 12.7), accepts only loopback, pod (k3s default CIDR) and mesh peers (403 otherwise), and answers 503 until the tor-remote-access app is installed. The gateway's TLS port is never the target, for the `tor-remote-access` app id only (fixed in the gateway, never asked for in a manifest). The LAN stays excluded and no other app gets it. Before this the app's init step stopped for lack of the address. Tests check the ConfigMap, the single /32 allowance, the order before the manifests, and that other apps or an unresolvable address get nothing. Still open on #284: the live test with real `tor`, the owner-approved onion passkey enrolment, and a Tor Browser cookie check.
