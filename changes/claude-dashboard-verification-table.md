Settings, Verification levels in the dashboard (D-028, gateway permissions design PR 16, issue 1213). An owner sees the table of how strongly OneMind checks it's you before each kind of approval or change: each row's level now as a badge, its default, the lowest and highest it may go, and the rows that are never eased before the first proven key (physical actions). Changing a row, or raising one kind of request above its row (for example L3 before an app is removed), files a verification.requirement.set request that waits in Approvals for a key at the table's own level; nothing is written directly. The page never offers a level below a row's floor, above L1 for data access, or L3 while no key on the box reaches it, and shows each change already waiting in Approvals with who asked for it: only the owner's own waiting request closes the row, so a guest's or a child's request never passes for the owner's. It also shows the box's state: the strongest key an owner holds, the first-key grace (L2 is any passkey plus the code on the box's own screen, or waits when the box has no screen) and recovery after the last proven key is gone. The page takes the owner's role from the shell, which reads GET /v1/me on a real hub, as the other owner-only screens do, and says it is checking until that answers. The Security overview links here. All calls go through @onemind/sdk to the existing gateway routes; the CLI already has the same table as onemind permissions verify.
