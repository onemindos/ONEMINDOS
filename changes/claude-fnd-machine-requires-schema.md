One requires / recommends / supports block in the app schema (#724). All three take the same keys ($defs/machineNeeds): `arch` (amd64, arm64, or x86-64-v1 to v4 for amd64 at a CPU level), `memoryMb`, `storageFreeGb`, `accelerator` (vendor-neutral `capability`, `minMemoryMb`, `rtCores`, `count`, `overlay`), `devices` (vendor-neutral device classes, reserved for bridges; nothing grants a device yet), `radios` (zigbee, thread, z-wave, lora, bluetooth) and `models.quantisations`. The older keys (`archs`, `gpu`, `minMemoryMb`, `cpuLevel`, `gpuCount`, `minVramMb`, `accelerator.optional`) stay valid, so every app in apps/ validates unchanged. `core/onemind_core/machine_needs.py` maps them both ways: `machine_needs()` gives the new shape, `legacy_requires()` gives the old one to the placement, CPU and GPU fit code, so an app written with the new keys is placed and refused exactly like one written with the old ones. The shared validators (the gateway's catalog check behind validate-apps, and `onemind plugin validate`) refuse an unknown key, a vendor resource such as nvidia.com/gpu or a host path in devices or accelerator.capability, one fact written in both spellings, an architecture named twice, and a requires.arch that differs from spec.archs, each with a plain message. The shared golden cases in sdk/testdata/manifest-v1 cover all of them.
