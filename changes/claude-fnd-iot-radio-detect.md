Known USB radio dongles now get stable names and a radio-found card (issue 732, first step of the LoRa messenger's dock mode). The image ships udev rules that give a Home Assistant Connect ZBT-1 or ZBT-2, SONOFF Zigbee Dongle Plus (P and E), ConBee II or III, or the CH340K USB serial chip of the Elecrow ThinkNode-M2 (`1a86:7522`) the name `/dev/onemind/<kind><n>` (kind `zigbee`, `zigbee-thread` or `lora`; the first LoRa radio is `lora0`) and the new `onemind-radio` group (mode 0660). A small helper, `/usr/lib/onemind/radio-name`, picks the lowest free number and never opens the device. The rules are rendered from one table, `sdk/schema/onemind.radios.json`, which the node agent and the gateway also read. The node agent reports each name in its heartbeat as a radio with its serial line and stable name (`device`), only while the USB device behind the link still matches the table. GET /v1/radios (nodes:read) shows a card for every USB serial line on every machine with kind, model, port and stable name; a known radio's card carries a stable id, `<node_id>.<kind><n>` (for example `3f9c2a1b7d4e.lora0`), that later radio routes use; any other USB serial device is listed with no kind and no name and can never be granted. The CH340K id is a generic chip, so a LoRa radio's card asks the owner to confirm it is a MeshCore companion (USB), with POST /v1/radios/{id}/confirm (owner only, audited, opens and sends nothing); the confirmation is stored in the gateway database for that radio on that machine and USB port, so it survives a restart, an OS update and a replug into the same port, and a radio on another port is asked again. The grant that passes a radio into an app comes with issue 854. Checked: the Debian 13 kernel (linux-image-6.12.117+deb13-amd64) builds `ch341` as a module that lists `1a86:7522`.
