Step 2 of the Debian bones, plan PR 6 (IMG-05, #152, stacked on #975): the image now keeps timeline snapshots of the owner's files and scrubs the data disk once a month, with Debian's own tools. snapper (0.10) takes an hourly timeline snapshot of the @storage subvolume at /data/storage only, keeps them in @storage/.snapshots (24 hourly, 7 daily, 4 weekly, 6 monthly) and cleans up daily; the k3s data and the databases are in the @ subvolume and are never snapshotted, and the root is read-only so it has no config. btrfsmaintenance runs btrfs-scrub monthly on /data, which reads every block and checks its checksum (one disk has no second copy, so it can report a bad block but not repair it). The configs are baked into /etc (the root is read-only): /etc/snapper/configs/storage, /etc/default/snapper (libsnapper takes its config list from there) and /etc/default/btrfsmaintenance; the package's refresh service, which rewrites timer drop-ins, and the balance, defrag, trim and snapper-boot timers are masked. The three services skip (a condition) on a box without /data/storage/.snapshots, an ext4 box installed before #152, so a failed unit never trips the health gate. #833's own snapshot scheduler is not used. New QEMU check E8 (test/qemu/CRITERIA-SNAPPER.md, pre-registered): a timeline snapshot appears from the real unit, a file copied from it matches byte for byte, a scrub finishes with no errors, and the snapshot survives an A/B update. The scrub's result stays readable: /var/lib/btrfs, where btrfs-progs writes the last scrub status, is bind-mounted from /data (the root is read-only), found when the first scrub reported no stats.
