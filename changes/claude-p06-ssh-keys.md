SSH keys and the SSH switch, from the owner's own screens (wave 2, P-06; stacked on the owner shell, #1099). The gateway has GET /v1/ssh and GET /v1/ssh/keys (owner only) and three owner actions through the approval queue: POST /v1/ssh/keys (add a key), DELETE /v1/ssh/keys/{id} (remove one) and PUT /v1/ssh (SSH on or off). Agents cannot ask for any of them; adding a key and switching SSH on need a passkey once passkeys are active, taking exposure away needs none. The gateway checks the public key (plain, a supported type, RSA at least 2048 bits) and shows its fingerprint on the approval card; the host service files one text job on the data partition and starts a new root oneshot, onemind-ssh-apply.service, which runs onemind-owner (new key-rm, ssh-on, ssh-off, apply-job; it never follows a symlink as root). Off is a flag file on /data that ssh.service tests, so it holds across reboots and updates. The ssh firewall chain now counts new connections per address and drops more than 6 a minute before sshd sees them. The dashboard Account page has an SSH keys card, and the CLI has onemind ssh-key add, list and rm, and onemind ssh on, off and status. First-boot check F23 (F20 before the round-2 integration renumbering; criteria pre-registered first) adds a key, removes a key and switches SSH off and on through the real approval path.

Second review fix: on the cloud boards, port 22 now goes through the same SSH chain as everywhere else, so the 6-new-connections-a-minute limit also covers the internet and port 22 closes when SSH is switched off. The SSH screen and the CLI no longer say "home network only" for a cloud box.

Third review fix: the rate limit now uses "update" on its counting set, so a source that keeps trying keeps its counter and stays at 6 new connections a minute (with "add" the entry expired a minute after the first try and the source got a fresh burst, about 12 a minute); checked on nftables 1.1.3, which also adds the IPv4/IPv6 check itself. GET /v1/ssh reports "internet" in reach on a cloud board (the host service sees the board's firewall file) and the SSH card says so there. Removing a key from the dashboard or the CLI sends an Idempotency-Key header, so a retry files one request, not two (the Go SDK gains DoIdempotent for this). The SSH card uses the generated SDK types. The cloud firewall file notes that SSH fails closed when the host firewall did not load, and that the provider's console is the way in then.
