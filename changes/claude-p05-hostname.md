Rename the box (P-05). The owner can change the box's name from Settings > About (Rename this box) or with `onemind name set NAME`; `onemind name show` prints it. The request is `PUT /v1/instance/name`, which files an `instance.rename` action that waits in Approvals: an agent or the CLI can ask, only an owner approves (D-027). Once approved, the host service (new kind `set-hostname`) saves the name on the data partition (the root is read-only), asks systemd-hostnamed to switch the running name, fixes the 127.0.1.1 line and restarts avahi, so the box answers as NAME.local at once; at every boot `onemindd host apply-hostname` (a drop-in of onemind-data-layout.service) puts the name back before avahi starts. The first rename also pins the Kubernetes node's name (K3S_NODE_NAME in /data/onemind/etc/k3s.env, read by k3s.service and the health gate), so a rename never turns the next boot into a new node that the local-path volumes do not belong to. The name is one lower-case DNS label, as the first-run setting already requires. Tests: Go unit tests for the host kind, the saved name, boot apply and the node pin; gateway tests for the owner-only approval, idempotent replay, refused names and the sign-in name following only a finished rename; CLI and dashboard tests; QEMU first-boot checks F13 (the rename reaches the running system and avahi) and F14 (it survives a reboot), pre-registered in CRITERIA-FIRSTBOOT.md section 9. Known limits: the phone app's box-settings screen still only edits the stored name, not the host name; the box CA's certificate lists the old `<box>.local` until the gateway next starts with the new name, while `onemind.local` names stay valid; and `onemind.local` itself stops answering after a rename because avahi publishes the host name.
