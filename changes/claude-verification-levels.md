Verification levels for approvals and owner changes (D-028, gateway permissions design PR 11). A new passkey is asked for direct attestation and saved with the level it can prove: L1 Device check for any passkey (phone passkeys that send attestation none, synced passkeys, keys whose model or certificate chain is not trusted, and responses in a format the gateway cannot verify all still enrol, at L1, with a plain explanation), or L2 Proven key for a device-bound key whose attestation chains to a trusted root for a model that lists a fingerprint or face check. No biometric data is ever received or stored. Approve-options now says which level an approval needs and offers only the keys that meet it; destructive and physical approvals and every security setting default to L2, everyday approvals stay L1. The owner can edit the verification table (GET /v1/verification-requirements; changes are verification.requirement.set requests approved at L2, never below each row's floor, and data access can never be raised above L1) and the trusted key models (authenticator.allowlist.add, removal is direct). Owner changes that need L2 use a step-up bound to the exact change (POST /v1/auth/step-up/options and /v1/auth/step-up, then the OneMind-Step-Up header). The 401 names that step-up in its details (operation, target and the body the hub binds), so the SDK's shared completeStepUp helper confirms it in place (asking for the box's code when needed) and repeats the request once: People and ordinary passkey enrolment keep working in the dashboard, any SDK caller gets the same, and the phone app confirms with its passkey, instead of asking to sign in again. Below L2 the same in-place step-up replaces signing in again, including removing a key. A phone passkey cannot meet L2, so the phone says to make that change on the dashboard; the CLI says the same. Until any owner has had a proven key (open question N-1, decided as the recommended option b), an L2 approval or change is accepted with any passkey plus a 6-digit code that only the box's own screen shows, and the API says grace; remotely it still needs L2. The code is written for the box's screen (onemind-screen on tty1) and never sent over the network; it works once, for 2 minutes, and five wrong codes pause it for 15 minutes. A box with no screen waits for a proven key. After the first owner passkey, an owner's new proven key needs that owner's own proven key or the code on the box's screen, before and after the grace and whatever keys the owner already has, so a passkey somewhere else can never enrol a key of its own that would be L2: not after deleting its owner's only key, not for an owner with no key, and not with the admin.high_risk row lowered to L1 (adding a proven key has its own floor, which the table's label says). A pending proven-key registration needs fresh options if the person became an owner or another owner passkey was added during initial setup. Only one owner can use the first-key exception, even when two owners enrol at the same time. Promoting someone who enrolled a proven key needs the same confirmation even if its model is no longer trusted. Trusting a key model during the grace needs the box too. The box-code enrolment flow is available through the API. Dashboard support for entering the code and proactively requesting a proven-key step-up is pending. The grace is one-way: once any owner has held a proven key it never returns, whether keys are deleted, a trusted model is removed or an owner is demoted. Removing the last proven key, or the model behind it, needs that key, or an owner at the box when it is lost; afterwards L2 actions wait for a recovery path instead of falling back to L1, and an owner at the box can enrol a new key. Approval and owner-change verification also stay in effect when no active owner has any passkey. Approved verification-table edits check again that L3 is still reachable. A request waiting for approval now carries required_level, so its card shows the key it needs before the owner tries. Physical actions and the motion lockout are never eased. CLI: onemind keys list/remove, onemind keys models list/add/remove, onemind permissions verify get/set, all with --json.

The first owner passkey permanently ends setup, including in L1-only households. Owners who lose every active passkey still need the code on the box to enrol a proven replacement. The gateway records the end of grace in the transaction that first establishes a proven owner key. Pending enrolments backed by a step-up check that the same session and confirming key still qualify when the new key is saved.
