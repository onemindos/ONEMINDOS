Verification levels for approvals and owner changes (D-028, gateway permissions design PR 11). A new passkey is asked for direct attestation and saved with the level it can prove: L1 Device check for any passkey (phone passkeys that send attestation none, synced passkeys, keys whose model or certificate chain is not trusted, and responses in a format the gateway cannot verify all still enrol, at L1, with a plain explanation), or L2 Proven key for a device-bound key whose attestation chains to a trusted root for a model that lists a fingerprint or face check. No biometric data is ever received or stored. Approve-options now says which level an approval needs and offers only the keys that meet it; destructive and physical approvals and every security setting default to L2, everyday approvals stay L1. The owner can edit the verification table (GET /v1/verification-requirements; changes are verification.requirement.set requests approved at L2, never below each row's floor, and data access can never be raised above L1) and the trusted key models (authenticator.allowlist.add, removal is direct). Owner changes that need L2 use a step-up bound to the exact change (POST /v1/auth/step-up/options and /v1/auth/step-up, then the OneMind-Step-Up header). Until any owner has a proven key, L2 rows accept L1 and the API says grace (open question N-1); physical actions and the motion lockout are never eased. CLI: onemind keys list/remove, onemind keys models list/add/remove, onemind permissions verify get/set, all with --json.
