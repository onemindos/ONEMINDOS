Verification levels for approvals and owner changes (D-028, gateway permissions design PR 11). A new passkey is asked for direct attestation and saved with the level it can prove: L1 Device check for any passkey (phone passkeys that send attestation none, synced passkeys, keys whose model or certificate chain is not trusted, and responses in a format the gateway cannot verify all still enrol, at L1, with a plain explanation), or L2 Proven key for a device-bound key whose attestation chains to a trusted root for a model that lists a fingerprint or face check. No biometric data is ever received or stored. Approve-options now says which level an approval needs and offers only the keys that meet it; destructive and physical approvals and every security setting default to L2, everyday approvals stay L1. The owner can edit the verification table (GET /v1/verification-requirements; changes are verification.requirement.set requests approved at L2, never below each row's floor, and data access can never be raised above L1) and the trusted key models (authenticator.allowlist.add, removal is direct). Owner changes that need L2 use a step-up bound to the exact change (POST /v1/auth/step-up/options and /v1/auth/step-up, then the OneMind-Step-Up header). The 401 names that step-up in its details (operation, target and the body the hub binds), so the SDK's shared completeStepUp helper confirms it in place (asking for the box's code when needed) and repeats the request once: People and adding a key keep working in the dashboard, any SDK caller gets the same, and the phone app confirms with its passkey, instead of asking to sign in again. Below L2 the same in-place step-up replaces signing in again, including removing a key. A phone passkey cannot meet L2, so the phone says to make that change on the dashboard; the CLI says the same. Until any owner has had a proven key (open question N-1, decided as the recommended option b), an L2 approval or change is accepted with any passkey plus a 6-digit code that only the box's own screen shows, and the API says grace; remotely it still needs L2. The code is written for the box's screen (onemind-screen on tty1) and never sent over the network; it works once, for 2 minutes, and five wrong codes pause it for 15 minutes. A box with no screen waits for a proven key. The first proven key is also added at the box, so a passkey somewhere else can never enrol a key of its own that would be L2, and trusting a key model during the grace needs the box too. The grace is one-way: once any owner has held a proven key it never returns, whether keys are deleted, a trusted model is removed or an owner is demoted. Removing the last proven key, or the model behind it, needs that key, or an owner at the box when it is lost; afterwards L2 actions wait for a recovery path instead of falling back to L1, and an owner at the box can enrol a new key. Approved verification-table edits check again that L3 is still reachable. A request waiting for approval now carries required_level, so its card shows the key it needs before the owner tries. Physical actions and the motion lockout are never eased. CLI: onemind keys list/remove, onemind keys models list/add/remove, onemind permissions verify get/set, all with --json.
