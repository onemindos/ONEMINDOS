Go back to the previous OS version (P-16, D-027 to D-029). The Updates screen now shows, for each machine, the previous system version in the other A/B slot and a Go back button. The button only files an os.rollback request; going back discards the running version, so an owner approves it with a passkey (a bare token or a signed-in session gets step_up_required), and the new onemind update rollback command only files the request (an agent token is refused with 403, since only a person may file a rollback). On approval the gateway sends the approved version to the host service, which re-reads RAUC, refuses unless the other slot is marked good, holds a known different version and no update is pending or on trial, then marks that slot active and restarts. It never runs rauc install. The health gate sees no trial marker and commits the old slot. The host holds the update engine's lock from before the boot order is flipped until the box is down, and puts the boot order back if the host service stops first; after the reboot it reports success only if the box runs the approved version, and the engine records the go-back (rolled_back, "went back from X to Y (owner request)") in the status and history. The gateway asks the host before it files or approves a request, so the version just left is not offered again. The version it left is written to the gate's bad-releases list, so the update service does not reinstall it at once and a second go back cannot swap the slots. GET /v1/os/updates gains a rollback object per machine and for the hub. A new QEMU test (make rollback, RB0 to RB4, CRITERIA-ROLLBACK.md) boots the previous slot through the real host service, RAUC and gate.
