Settings, Standing approvals in the dashboard and the CLI (issue 1214). An owner sees each standing approval (what it covers, who may ask, today's use against its daily limit, the maintenance window, when it ends and whether it is on, paused or ended) and can create one, turn a paused legacy one back on, or remove one after a second click. The page takes the owner's role from the shell, which reads GET /v1/me on a real hub, as the other owner-only screens do. The page says in plain words what a standing approval can never cover (sensitive or destructive requests, everyone at once, more than 90 days, an agent that reads outside text) and checks a new one before sending it. Creating and turning back on are confirmed in place through the SDK's shared step-up helper (the proven key, or before the box's first proven key any passkey plus the code on the box's own screen); removing goes through at once. The CLI gets onemind actions policies list, create, confirm and remove (--json); create and confirm point to the dashboard when the hub wants a passkey. The gateway documents the ApprovalPolicy answer of the list, create and confirm routes in the OpenAPI spec (answers unchanged), so the dashboard reads it through generated SDK types. The Security overview and the Automation page link here. On a phone the Name cell also says when each standing approval ends and its window (by name), and the Ends column stays visible, so a paused one can be checked before it is turned back on. If the agents, automations or maintenance windows can't be loaded, the form says so instead of quietly offering only "Any time". A change refused because the sign-in lapsed signs out.
