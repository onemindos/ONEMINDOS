Firewall: allow rules with automatic revert (P-09 part 2, refs #239). The owner can open one port to the home network (LAN) or the mesh, and the box takes it away again unless the owner confirms it. `POST /v1/network/firewall/allow` (and `onemind firewall allow tcp/8123 --scope lan or --scope mesh`, and "Ask to open this port" on the Network screen) only files a `firewall.allow` request: an owner or an agent may ask, only an owner approves, and only with a passkey. After approval the rule is pending; it closes by itself after 5 minutes unless it is kept (`onemind firewall confirm ID`, or "Keep it open"). Confirming and removing are owner only and audited; removing needs no approval. The internet is not a scope: only `lan` and `mesh` exist, the host writes into two chains that are reached only from the private-address chain and from the mesh interface, and it checks every value again. A rule that was not confirmed also disappears when the host service restarts or the box reboots; confirmed rules come back from /data. The host service gains no network privilege: it hands a file to a new unit, `onemind-firewall-owner.service`, which holds only CAP_NET_ADMIN. The firewall view lists the opened ports with their state and deadline. A QEMU check (FW6 to FW8, pre-registered as FW5 to FW7 and renumbered in the round-2 integration; criteria pre-registered in `test/qemu/CRITERIA-FIREWALL-ALLOW.md`) proves an unconfirmed rule reverts and a confirmed one survives a host service restart.
 A rule whose reload fails never leaves a port open that nothing tracks: the previous file is written back, and a revert that cannot load stays listed as `revert_failed` (removable) and is retried with backoff. The LAN scope also reaches mesh peers and apps on the box, and the screen says so.
