Settings, Security, Sign-in keys in the dashboard (D-028, gateway permissions design PR 17). Each passkey and security key shows its verification level as a badge (L1 Device check or L2 Proven key), its model, whether it syncs between devices or stays on one, and, for a key that can only reach L1, the plain reason. Adding a key runs the browser's passkey ceremony; once you hold a proven key, the dashboard asks it to vouch for the new one with a step-up bound to that change, made in place through the SDK's shared step-up helper. Removing a key asks for a fresh passkey check in place. Removing your last proven key is warned about first: high-risk approvals will need a recovery path until you add another strong key, and never go back to a Device check key; it confirms with that key, or, when the key is lost, with any passkey plus the code on the box's own screen. Before the box's first proven key, adding one asks for that code too, because the first proven key is added at the box. A two-key nudge asks for two proven keys so losing one is never a lock-out, says that until then high-risk approvals are confirmed at the box, says when they wait for a new key after the last one is gone, and says your files never depend on a proven key. Owners see the trusted key models, can stop trusting one after a confirm step that names the keys dropping to Device check, and can ask to trust another, which waits in Approvals for a proven key. The Security overview now counts registered and proven keys and links here. In Approvals, a request that needs a proven key the owner does not hold is explained in plain words (which key, where to add it), and its card then shows the level it needs. All calls go through @onemind/sdk to real gateway routes.
